# 落とし穴の記録

一度はまって、原因の特定に時間がかかったもの。
どれも「見た目では気づけない」か「黙って失敗する」たぐいで、
知らずに触ると同じところで止まる。

該当する領域を触る前に、その節を読むこと。

---

## Cesium

### PolylineVolumeGeometry の断面は外接矩形で正規化される

`PolylineVolumeGeometry` に渡した断面（`shapePositions`）は、
内部の `convertShapeTo3D` が **x も y も外接矩形のぶんだけ引く。**
つまり断面に書いた y の絶対値は無視され、
**中心線の高さから必ず上へ**押し出される。

```
node_modules/cesium/Build/CesiumUnminified/Workers/chunk-FBP4DUQJ.js
```

「梁を中心線の下にぶら下げよう」として断面に負の y を書いても、
そのぶん上にずれるだけで、見た目からは何も分からない。

**書き方の決まり:**
- 断面は必ず **y = 0 を下端**として書く
- 中心線には、その部材の **下面**の高さを渡す

`packages/map-engine/src/elevated-structures.ts` はこの規約で統一してある。
検証は `__tests__/elevated-structures.test.ts` が頂点座標を実測している。

### Cesium3DTileStyle の式に `defined()` は無い

スタイル式で使えるのは `isNaN()` / `isFinite()` だけ。
`defined()` を書くと式全体が失敗し、**スタイルが丸ごと当たらない。**
例外は出ず、ただ色が付かないだけなので気づきにくい。

これが原因で、遠景タイルセットのスタイルが全都市で一度も適用されていなかった。

### コロンを含む属性は `${feature['...']}` でしか読めない

```
${bldg:usage}              パースエラー（Unexpected ":" at character 8）
${['bldg:usage']}          パースは通るが常に undefined（黙って失敗する）
${feature['bldg:usage']}   正しい
```

2 番目が最も危険。エラーが出ないまま全条件が外れる。
`packages/map-engine/src/building-style.ts` では属性名を定数にまとめ、
書き間違いが一箇所で済むようにしてある。

### `color('#rrggbb') * 0.96` はアルファまで掛かる

明度を落とすつもりで掛け算すると、アルファも 0.96 になって半透明になる。
建物が薄くなり、奥の建物が透けて見える。

```
vec4(r * S, g * S, b * S, 1.0)   … アルファは明示的に 1.0
```

### `Primitive` は add した直後には何も描かれない

`asynchronous: true`（既定）の `Primitive` はワーカーで頂点を組むので、
`scene.primitives.add()` した直後は `ready` が false で、まだ何も出ていない。

古いものを先に消して新しいものを add すると、
組み上がるまでの数秒間そこが空白になる。これがちらつきの正体。

**新しいものが `ready` になってから古いものを消す。**
`packages/map-engine/src/primitive-swap.ts` の `waitForPrimitives` を使う。
`requestRenderMode` では描画が走らないと組み立ても進まないので、
待っている間はこちらから `scene.requestRender()` を呼ぶ必要がある。

### 地表に貼る帯は、細いものを面で描くと消える

区画線の実寸は 0.15m。これを `CorridorGeometry` の面として地表に貼ると、
少し離れただけで 1 画素を割って見えなくなる。

実際の地図やカーナビは、区画線を「画面上の太さ」で描いている。
`packages/map-engine/src/scene-renderer.ts` では 0.5m を境に、
太いものは面（`CorridorGeometry` + `GroundPrimitive`）、
細いものは線（`GroundPolylineGeometry` + `GroundPolylinePrimitive`）で描く。

破線の刻みも同じ理由で画素基準になる（`PolylineDash` の `dashLength` は
画素単位で、メートルでは指定できない）。実寸で刻めるのは横断歩道のような
太い縞だけ。位置と本数は実データどおりで、近似しているのは刻みの細かさだけ。

### 地理院タイルにはズーム 0 と 1 が無い

`minimumLevel` を指定しないと、Cesium はズーム 0 から読もうとして 404 になる。
その結果、引いた状態で地球に何も貼られず、**縮小すると日本地図が消えたように見える。**
エラーは画面に出ないので、黒いことしか分からない。

実測（2026-09、cyberjapandata.gsi.go.jp）:

| レイヤ | 提供ズーム | 範囲 |
|---|---|---|
| seamlessphoto / std / pale | 2〜18 | 世界中（北米 5/7/12・欧州 5/16/10・豪州 5/28/18 で 200 を確認） |
| blank | 5〜14 | 日本国内のみ（国外は 404） |

`minimumLevel` を上げるほど全球を覆う枚数が増える（4^n 枚）。
ズーム 2 なら 16 枚なので、起動の負担にはならない。
国内にしか無いレイヤは `rectangle` で範囲を区切り、無駄な 404 を出さない。

### 描画距離は毎フレーム合わせる

`frustum.far` の更新を 0.5 秒間隔の監視処理に相乗りさせていたため、
慣性の効いたズームで高度が一気に変わると far が追いつかず、
地球がクリップ面の外に出て一瞬消えていた。

far の計算は数回の乗除算なので毎フレームでよい。
一方、上限を超えたカメラの引き戻し（`setView`）は毎フレームやると
カメラ操作と競合するので、監視と同じ間隔のままにする。

### `geometricError: 1e+100` は必ずしも「全部読む」ではない

台東区の tileset.json は根の `geometricError` が `1e+100` になっている。
一見「打ち切りが効かず全タイルを読む」ように見えるが、
深さ 0〜14 は子を 1 つだけ持つ空の入れ物で、
深さ 15 以降は正常な値（64 → 32 → 16 → 8）に戻る。
SSE による打ち切りはちゃんと効いている。

（当初これを「無条件に 797 タイルを読む」と誤って判断した。
 実際に json を辿って数えるまで結論を出さないこと。）

### 時計を進めると `requestRenderMode` が効かなくなる

`clock.shouldAnimate = true` にすると、時刻が変わるたびに再描画が要求される
（`Scene.maximumRenderTimeChange` の既定は 0 で、どんな変化でも描き直す）。
静止中に描かないという省電力の仕組みが丸ごと無効になり、
「現在時刻に追従」を選んだだけで iPhone が発熱し続ける。

太陽は 1 分で 0.25 度しか動かない。時計は止めたまま、
こちらから 1 分ごとに `currentTime` を入れ直せば、
見た目は同じで描画は 1 分に 1 回で済む。

**そして「一度だけ適用して終わり」にしない。**
以前は追従を入れた瞬間の 1 回しか適用しておらず、
昼に追従を入れたまま夜になっても環境光は昼のまま、星も出なかった。
太陽の位置は Cesium が時刻から計算してくれるが、
夜の補正・星空・環境光は自分で入れ直さないと切り替わらない。

## 数値と反復

### 距離で刻むループは、進まない刻み幅で止まらなくなる

経路を「線 8m・空き 12m」で刻む処理で、無限ループを作って
テストが 120 秒でタイムアウトした。

```
const remaining = inLine ? on - phase : period - phase;
const step = Math.min(remaining, segment - cursor);
cursor += step;   // step が 0 だと永久に進まない
```

位相がちょうど境目に乗ると `remaining` が 0 になり、`cursor` が
進まないまま回り続ける。浮動小数の計算では「ちょうど乗る」ことが起きる。

**距離を足して進めるループには、必ず前へ進む最小の刻みを入れる。**

```
const remaining = Math.max(1e-6, inLine ? on - phase : period - phase);
```

### 緯度経度の引き算は割り切れない

`34.71 - 34.7` は `0.00999999999999801` になる。
格子点ちょうどを指しても最後の桁がずれるので、
座標から求めた値を厳密な一致で検証してはいけない。
許容誤差を決めて比較する（標高なら 1mm で十分）。

## OpenStreetMap

### `bridge=yes` + `layer=1` は「水路の上」かもしれない

`layer` を「高架の階数」と解釈すると、川に架かるだけの普通の橋が
路面から 4〜5m 浮く。

浜松の実測（2026-08）: 道路橋 56 本のうち **56 本すべてが水路を渡る橋**だった。
`layer=1` は道路ではなく水路との上下関係を表していた。

対処: Overpass のクエリに水路（`waterway=river|stream|canal|drain|ditch`）を含め、
経路が水路と交差するかで桁下高を決める。
`packages/gis/src/structures.ts` の `crossesWaterway` / `deckHeightOf`。

桁下高の実際の値:
| | 水路の上 | 道路・線路の上 |
|---|---|---|
| 道路 | 1.2m | 5.6m |
| 歩道 | 1.6m | 5.6m |
| 鉄道 | 1.8m | 6.5m |

### 線路は 1 本ずつ別の way になっている

複線・多線区間でも `railway=rail` の way は線路 1 本ごとに分かれている。
そのまま構造物として扱うと、高架が何十本も重なって描かれる。

浜松の実測: 新幹線の高架部で **15 本**、軌道中心間隔 3.8〜4.3m
（日本の標準は 4.1m）。

対処: `packages/gis/src/structure-merge.ts`
1. 端点が近いものを縦につなぐ（`stitchStructures`）
2. 平行に走るものを横にまとめる（`mergeParallel`、Union-Find）
3. 基準線に沿って幅を測り、変わるところで区間に分ける（`segmentByWidth`）

これで重なりが 110 組から 9 組に減った。

### `<node>` の解析で先読みを使うと 1 件も取れない

以前のパーサは「次の要素が始まるところまで」を先読みで探していた。

```
/<node\s+([^>]*?)(\/)?>([\s\S]*?)(?:<\/node>)?(?=<node|<way|<relation|$)/g
```

実際の XML は `</node>` と次の `<node>` の間に改行と字下げが入るため、
この先読みが一度も成立せず、**ノードを 1 件も取り出せていなかった。**
信号・横断歩道・街路樹はすべてノードなので、これらが丸ごと落ちていた。

閉じタグそのものを終端にすれば、間に何が入っていても取れる。

```
/<node\b([^>]*?)(?:\/>|>([\s\S]*?)<\/node>)/g
```

（`packages/gis/src/osm-api.ts`。`parseOsmXml` は検証のために export してある。）

### `layer > 0` は「高架」を意味しない

OSM の `layer` は **交差する相手との相対的な重なり順**であって、
地面から浮いていることの根拠ではない。地上の線路が道路と交差するところにも、
建物の中を通る通路にも付く。浮いていることを示すのは `bridge` タグのほう。

`layer > 0` だけで高架にしていたときの実測（2026-09、東京駅周辺 4km 四方）:

| 誤って建てていたもの | 本数 | 例 |
|---|---:|---|
| トンネル・屋内の通路 | 92 | `tunnel=building_passage` の 30m の通路 |
| 駅構内の階段・通路 | 162 | 9m の階段、1m の footway |
| 線路の交差部だけ | 40 | 8m の `railway=rail` |

判定の決まり:

- `tunnel` が付いていたら建てない（`tunnel=building_passage` も含む）。
  `covered` では落とさない — 覆いのある高架が実在する（東北新幹線）
- `bridge` が無いものを建てるのは、**長く続いていて（250m 以上）
  かつ上の層にある**ときだけ。市街地の鉄道高架は OSM で bridge が
  付いていないことがあるので、そこだけ拾う
- 歩行者用（footway / steps / path / pedestrian / cycleway）は
  **`bridge` があるときだけ**。本物の歩道橋・ペデストリアンデッキには
  bridge が付く。無いまま上の層にあるものは駅の構内通路やビルの中の通路で、
  名前を見ると「JR秋葉原駅;3階;5番線」のようになっている

修正後、東京駅周辺で誤りは 0 になり、
鉄道高架は 309 → 190 本、歩道橋は 458 → 293 本になった。

### 車線数の補完値から幅を逆算しない

OSM の道路タグの充足率は低い。浜松駅周辺 3km 四方の実測（2026-08）:

| タグ | 入っている割合 |
|---|---|
| `lanes` | 7% |
| `maxspeed` | 3% |
| `width` | 0% |

足りないぶんは道路構造令の標準値で補うが、
**補完した車線数からさらに幅を計算してはいけない。**
生活道路も 3 級道路もどちらも「対面 2 車線」に補完されるので、
逆算するとどちらも同じ 7m になり、道の格の違いが消える。

幅は「実データ → 実データの車線数 → 種別ごとの標準幅」の順で決める。
（`packages/gis/src/road-geometry.ts` の `roadWidthOf`。
 この誤りはテストが検出した。）

### 「地表に描かない」と「高架として建てる」は必ず同じ判定にする

高架は 2 か所で扱う。

- `structures.ts` … 高架として立体を建てる
- `road-geometry.ts` … 高架の区間は地表に描かない

この 2 つが食い違うと、**どちらからも描かれない道や線路**ができる。
エラーは出ず、ただ何も無い場所ができるだけなので気づきにくい。

実際に起きた。高架の判定を「layer > 0」から
「bridge があるか、250m 以上続いて上の層にある」に直したとき、
地表側は古いまま「layer > 0 なら描かない」だった。
結果、layer=1 の短い線路が高架としても建てられず、
地表にも描かれなくなっていた。

実測（2026-09、東京駅周辺 4km 四方）で消えていたもの:

| | 本数 |
|---|---:|
| `railway=rail`（東海道本線・京浜東北線など） | 68 |
| `highway=footway` | 41 |
| `highway=steps` | 23 |
| その他 | 4 |

浜松駅周辺では 0 本だった（線路がすべて bridge 付きの高架のため）。
地域によって出方が違うので、1 か所で確かめて安心してはいけない。

いまは地表側が `classify()` をそのまま呼ぶ形にしてある。
判定を分けて書くと、また離れる。

### `Number(null)` は 0 になる

クエリの数値を素朴に読むと、「指定が無い」ことと「0 が指定されている」ことを
区別できない。

```
const lat = Number(url.searchParams.get('lat'));   // 未指定なら 0
if (!Number.isFinite(lat)) return 400;             // 0 は有限なので通る
```

`/api/poi` はこれで、**引数の無い要求を「緯度 0・経度 0（大西洋）」として
受け付けていた。** 実際に 200 が返ることを確かめた。

`Math.min(Number('abc'), 20)` が NaN になるのも同じたぐい。
件数や半径が NaN のまま外部への問い合わせに渡っていた。

`packages/shared/src/geo.ts` の `parseNumberParam` /
`clampNumberParam` / `parseLatLngParam` を使う。
検証を 1 か所に集めておかないと、API が増えるたびに同じ穴が空く。

### 壊れた経路は「例外」ではなく「NaN」で来る

polyline のデコードは壊れた文字列でも例外を出さない。
`decodePolyline('!!!@@@###')` は緯度 -33.5 のような座標を 5 点返す。
経路エンジンの応答が壊れていても、そのまま案内が始まってしまう。

止め方を 3 段階に分ける:

1. **API で弾く** … `/api/route` が、座標が 2 点以上あり、
   すべて有限で地球上にあることを確かめる。壊れていれば 502 を返す
2. **ライブラリは落ちない** … 座標が空でも 1 点でも例外にせず、
   進捗 0 として返す。ここで落ちると画面が真っ白になる
3. **カメラの姿勢は必ず有限にする** … NaN を渡すとカメラが画面の外へ
   飛び、操作しても戻らない。`sanitizePose` で最後に落とす

測位（GPS）も同じで、まれに NaN を返す。そのまま進捗に入れると
距離も方位も NaN になり、正しい位置に戻っても復帰しなくなる。
`RouteFollower` は使えない位置を無視して前回の位置で進める。

### OSM のタグの値には上限を掛ける

OSM のタグは自由入力なので、入力ミスや荒らしで極端な値が入る。
`tracks=1000000000` をそのまま使うと、線路を 10 億本組み立てようとして
ブラウザが固まる（実際に固まることを確かめた）。

上限は実在するものの最大に合わせる:

| タグ | 上限 | 根拠 |
|---|---:|---|
| `tracks` | 40 | 世界最大級の駅でも 30 本程度（東京駅は 20 面 20 線） |
| `lanes` | 24 | 最多はカナダのハイウェイ 401 で往復 18 車線 |
| `width` | 100m | 道路の幅は最大でも 100m 程度 |
| `layer` | ±6 | OSM の慣習は -5〜5。立体交差でも 4 層で足りる |

**描く側でも同じ上限を掛ける。** 呼び出し側が忘れても固まらないように。

### 0 除算は「NaN が並ぶ」形で出る

`pickIndices(length, max)` は `(i * (length - 1)) / (max - 1)` で
添字を等間隔に取るが、`max` が 1 だと分母が 0 になり、
NaN の配列が返っていた。例外にはならず、そのまま座標に流れる。

**割る前に分母が 0 になりうるかを確かめる。**
NaN は例外を出さずに伝播し、描画側では「何も出ない」という形でしか
現れないので、原因にたどり着くのに時間がかかる。

地形の取得に失敗したときの NaN も同じ。標高を使う前に
`Number.isFinite` で確かめて、取れなければ 0（平地）として扱う。

### 速度制限は推測しない

`maxspeed` が入っていないときは表示しない。
種別から推測すると、実際とは違う数字を標識のように見せることになる。
`JP:urban` のような記号も数値ではないので採らない。

## 外部サービスの応答

### 配列があるはずの場所が `undefined` で来る

経路エンジン（Valhalla / OSRM）の応答は、混雑時や部分障害のときに
項目がまるごと欠けて返ってくる。`trip.legs` や `route.legs[].steps` が
無いまま HTTP 200 で届く。

そこに `for...of` や `forEach` を当てると `TypeError` になり、
**その英語の内部メッセージがそのまま利用者の画面に出る。**
実測で 7 通りの欠け方が例外になっていた:

| 欠けているもの | 出ていたメッセージ |
|---|---|
| `trip.legs` | `trip.legs is not iterable` |
| `trip.summary` | `Cannot read properties of undefined (reading 'length')` |
| `leg.maneuvers` | `Cannot read properties of undefined (reading 'forEach')` |
| 形状が空なのに案内がある | `Cannot read properties of undefined (reading '0')` |
| `routes[].legs` | `r.legs is not iterable` |
| `leg.steps` | `leg.steps is not iterable` |
| `maneuver.location` | `Cannot read properties of undefined (reading '0')` |

対処は 2 つ。

1. **応答の型を「省略可」で書く。** 仕様上は必須の項目でも `?` を付ける。
   必須で書くと、存在を確かめる分岐が「到達しない」と型検査に消される
2. **形にならなければ `RoutingError` で打ち切る。** 座標が 2 点未満なら
   経路として返さない。こうするとフォールバック側（OSRM）に回せる

数値の欠けも同じで、`m.length` が無いと `Math.round(undefined * 1000)` が
NaN になり、残距離も到着時刻も表示できなくなる。0 に落として先へ流す。

### polyline の文字列は連結してはいけない

polyline は「直前の点からの差分」で書かれている。
レグごとの `shape` をつないで 1 本の文字列にすると、
2 本目の先頭が「1 本目の末尾からの差分」ではなく
「原点からの差分」として解釈され、**経路が日本から飛ぶ。**

つないだ座標列から `encodePolyline` で符号化し直す。

### 案内の添字は 0 以上に収める

`begin_shape_index` が範囲外や負で来ることがある。
負のまま残すと `cumulative[index]` が `undefined` になり、
`?? 0` で 0 に落ちて「出発した瞬間に通過済み」の案内になる。
`[0, 座標数-1]` に収めてから記録する。

### LLM が書いた数値は範囲を確かめる

AI のツール呼び出しは、座標だけでなく**数値も信用境界**にある。
LLM は学習した別サービスの仕様をそのまま書いてくるので、
未対応の移動手段（`car`）、負の半径、上下が反転する俯角（-400 度）、
地面の中になる高度（0）が普通に届く。

座標を `knownPoints` で検証しているのと同じ理由で、数値も範囲に収める。
`Math.min(value, 上限)` だけでは負の値が素通りすることに注意。

### 神戸市には 3D 都市モデルが無い

datacatalog に建物モデルが存在しない。対応都市から外し、
LOD2（テクスチャあり）が揃っている **姫路市（28201）** に差し替えた。
対応都市を増やすときは、まず datacatalog に実データがあるか確かめる。

### near と far が同じ四分木を指すことがある

浜松では近景用と遠景用のタイルセットが同一の四分木を返していた。
結果、同じ建物が二重に描かれ、タイルの取得も 2 倍になっていた。

`packages/map-engine/src/buildings.ts` の `needsFarTileset(city)` で、
近景がすでに直接タイルセットを指している都市では遠景を作らない。

### 端をかすめるだけの区まで開いてしまう

東京は 8 区にまたがるが、そのうち 4 区は表示範囲の端をかすめるだけで、
それが総タイル数の半分を占めていた。

`app/api/tileset/route.ts` で、重なり **面積**の大きい順に並べ、
上限（近景 5・遠景 10）まで残す。
これで tileset.json が 4.3MB → 2.2MB、タイル数が 3,555 → 2,571 になった。

## 座標と幾何

### 方位角の計算に `cos(緯度)` を忘れない

経度 1 度あたりの距離は緯度によって変わる。
これを忘れると柱が構造物に対して斜めを向く。
北緯 34.7 度では約 18% ずれ、45 度方向の柱の見付けが √2 倍に膨らむ。

検証: `elevated-structures.test.ts` の
「斜めに走る高架でも柱が構造と平行に立つ」が実際に見付け幅を測っている。

### 高さの基準は「路面」から下へ取る

桁下を基準にすると、同じ路線でも構造形式が変わる接続部で路面に段差ができる
（実際に 1.2m の段ができていた）。

```
deckTop    = 地盤 + deckHeight   路面（軌道面・車道面）
slabBottom = deckTop - 版厚      床版の下面 = 梁の上面
beamBottom = slabBottom - 梁高   梁下。柱の頭でもある
```

さらに、つながっている構造物どうしで路面高を揃える（`alignDeckHeights`）。
