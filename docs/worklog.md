### 盛土と取付部

利用者からの指摘: 「高架じゃない所もそうなってるし、普通の道から高架に
なる所も追加して欲しい。滑らかなやつで」

**高架じゃない所が高架になっていた原因**は `embankment=yes` の無視だった。
OSM がこう書いているのは「土を盛って持ち上げてある」という意味で、
柱の上に載っているという意味ではない。これを高架橋にしていたため、
盛土の区間に径間 8.9m の柱が延々と並んでいた。

実測（東京駅周辺 2km 四方、2026-09）: bridge の無い構造物 35 本のうち、
東北新幹線・東海道新幹線・京浜東北線の盛土区間が該当。
盛土として組み直した結果、形の総数は **6,291 → 4,218**（33% 減）。

**取付部**は、高架に端点を共有している OSM の道を、
その高架の路面高さまで標準の縦断勾配で上げて作る。

| | 浜松駅 2km | 東京駅 2km |
|---|---:|---:|
| 取付部 | 91 本 | 70 本 |
| 勾配（最小 / 中央 / 最大） | 5.0 / 7.0 / 9.7% | 3.5 / 6.1 / 7.2% |
| 長さ（最小 / 中央 / 最大） | 12 / 17 / 32m | 17 / 32 / 223m |
| 形の数（カメラ 50m） | 5,018 | 4,218 |
| 形の数（カメラ 400m） | 2,790 | 2,608 |

上端が接続先の路面と一致すること、勾配が基準に収まっていること、
壁が地面から路面まで届いていることを座標で検証し、問題 0 件。

### 高架へ上がる階段

利用者からの指摘: 「高架下から上に上がるタイプの 3D モデルがない」

歩道橋やペデストリアンデッキは必ずどこかで地表とつながっているのに、
その階段が無く、デッキだけが空中に浮いていた。

実測（浜松駅周辺 1km 四方、2026-09）:

| | 本数 |
|---|---:|
| `highway=steps` の way | 19 |
| うち高架のデッキに端点が接している | 5 |
| 3D の階段として組み上がった | 5 |
| うち段を 1 つずつ刻めた（平面形が足りた） | 4 |

高さは「上がった先の構造物の路面高さ」から取る。
段は蹴上げ 0.15m（立体横断施設技術基準）から数を決め、
踏面は平面形の長さを段の数で割って求める。
詳しくは `docs/pitfalls.md` の「高架に上がる階段は、上がった先からしか
高さが決まらない」。

描画負荷（東京駅 2km 四方、階段 11 本）:

| カメラ距離 | 形の数 | 階段ぶん |
|---|---:|---:|
| 50m | 6,291 | +444 |
| 400m | 3,460 | +49 |

踏面 0.30m は 300m 離れると画面上でおよそ 1 画素になるので、
そこから先は段を作らず斜めの段裏と手すりだけにする。

### 時間帯と天候を実際の値で決める

「天候システムも意味ないし時間帯もリアルじゃない」という指摘への対応。

**時間帯。** 昼夜の判定が「5:30 より前と 18:30 より後は夜」という
固定の閾値だった。日本の日の出・日の入りは季節で 2 時間半動くので、
12 月の 17 時が昼、6 月の 5 時が夜になっていた。どちらも実際とは逆。

`packages/shared/src/sun.ts` に太陽位置の計算を置いた
（NOAA Solar Calculator の式。Cesium を import しないので Swift へ持っていける）。
国立天文台 暦計算室の値と照らして 4 分以内で一致する:

| | 日の出 | 日の入り |
|---|---|---|
| 東京 夏至 | 04:25 | 19:00 |
| 東京 冬至 | 06:47 | 16:32 |
| 東京 春分 | 05:44 | 17:53 |

明るさは段で切り替えず、`daylightStrength()`（0〜1）を掛けて連続的に変える。
段だと日の入りの瞬間に街全体の明るさが飛ぶ。

見ている場所でも変わる。夏至の日の入りは根室 19:01・那覇 19:24 で 23 分違うので、
カメラが都市をまたいだら計算し直す（0.5 度以上動いたときだけ）。

**天候。** 以前は霧の濃さと空の彩度をわずかに動かすだけだった。
実際に変わるのは視程・直射日光・影の 3 つで、そこを動かす:

| | 視程 | 直射日光 | 影 |
|---|---|---|---|
| 晴れ | 30km | 1.0 | できる |
| 曇り | 14km | 0.45 | できない |
| 雨 | 6km | 0.22 | できない |
| 雪 | 2.5km | 0.3 | できない |
| 霧 | 0.7km | 0.35 | できない |

視程は気象庁の視程階級に対応させた（霧の定義が「視程 1km 未満」）。
影の有無が最も効く。曇りの日に建物の影が地面に落ちていると、
空をどれだけ灰色にしても晴れにしか見えない。

`packages/map-engine/src/__tests__/environment.test.ts` で
冬至 17:00 が夜・夏至 05:00 が朝になること、根室と那覇で判定が分かれること、
天候ごとに霧の濃さ・日射・影が動くことを測っている。

### 建物モデルの見え方を選べるようにする

「建物のテクスチャありか、浜松と同レベルの LOD にするかを東京でも
選択できるようにして」への対応。

同じ地域について PLATEAU は 3 通りの配信を持っているので、そのまま選択肢にした。

| | 東京での整備 | タイル数（千代田区） | 1 枚の平均 | 区全体 |
|---|---|---:|---:|---:|
| 実写テクスチャ | 62 市区町村 | 633 | 695KB | 約 440MB |
| 用途で塗り分け | 45 市区町村 | 633 | 345KB | 約 218MB |
| 箱型（LOD1） | 62 市区町村 | 20 | 4.65MB | 約 93MB |

「用途で塗り分け」は浜松と同じ見え方で、通信量がほぼ半分になる。
箱型は総量こそ最小だが 1 枚が 4.65MB と大きく、通信では有利にならない。
軽くなるのは頂点数と描画のほう。

気をつけた点が 3 つある。

1. **テクスチャ無し版だけ整備範囲が狭い**（45 / 62）。
   未整備の区で街が消えないよう、中身が無ければ元の指定へ戻す。
2. **戻すときに LOD は落とさない。** 落とすと「用途で塗り分け」を選んだだけで
   箱型になり、選んでいないものが出る。
3. **戻したことを描画側へ伝える。** tileset.json の `extras` に実際に配信した
   種別を入れる。要求した値のまま用途色を塗ると、実写テクスチャの上に色が乗って
   事実と違う色になる。

浜松・姫路は区ごとの tileset.json を URL で直接指しているため選択肢は 1 つ。
URL は特定 LOD・特定テクスチャの実体そのものを指していて、差し替えられない。

切り替えは近景の読み直しで、新しいほうが出そろってから差し替える
（カメラ追従の取り直しと同じ待ち合わせ）。街から建物が消える瞬間はない。

### 車線案内（どの車線に寄るか）

市販カーナビと Yahoo! カーナビにある機能で、交差点の手前で寄る車線を出す。
運転中にいちばん効く情報なので、カーナビ相当を名乗るなら要る。

**出典は OSM の `turn:lanes`**（例: `left|through|through;right`）。
経路エンジンがそれを解釈して、車線ごとの矢印として返してくる。

公開デモ（router.project-osrm.org）で東京駅 → 新宿駅を引いて、
実際の応答の形を確認した（2026-09）:

```
15 の step のうち 3 つが車線情報を持っていた
{"valid": false, "indications": ["left"]}
{"valid": true,  "indications": ["straight", "left"]}
現れた語: left / straight / slight right / right
```

気をつけた点:

- **無ければ出さない。** OSM に `turn:lanes` が無い交差点では
  経路エンジンも返さない。車線数から矢印を組み立てると、
  実在しない案内で車線を寄らせることになる
- **マニューバ地点の車線だけを使う。** OSRM は step 中に通る交差点を
  すべて並べる（実データでは 1 つの step に 29 個）。
  途中の交差点にも車線が付くが、それは通過点の話
- **数えられる言い方をする。** 「中央の車線」ではなく「左から 2 番目」。
  運転席から数えられるのは左端からの本数だけ
- 読み上げは 300m 手前で 1 回だけ。60km/h でおよそ 18 秒あり、
  1 車線ぶん寄れる

### 方面案内（案内標識の行き先と路線番号）

高速道路の分岐で「E1 横浜・静岡方面」と出る、あれ。
出典は OSM の `destination` / `destination:ref` / `ref`。

公開デモで東京駅 → 御殿場を引いた実際の応答（2026-09）:

```
{"name": "東名高速道路", "destinations": "E1: 横浜, 静岡"}
{"name": "", "destinations": "138: 山中湖, 箱根"}
{"name": "玉川通り", "ref": "246", "destinations": "三軒茶屋"}
{"name": "日比谷通り", "ref": "1; 20"}      国道 1 号と 20 号の重複区間
```

コロンの前が路線番号、後ろが行き先。カンマ区切りの行き先は
日本の案内標識の書き方に合わせて「・」で並べる。
セミコロン区切りの路線番号も同じ。

路線番号は四角で囲んで出すが、**色は付けない。**
国道・都道府県道・高速で色を分けたいところだが、
OSM の `ref` から確実に見分けられるとは限らない。
番号の意味を推測して色分けすると、実在しない案内になる。

音声でも「300メートル先、横浜・静岡方面、右方向です」と、
標識と同じ語で言う。

#### Valhalla も同じものを返す（2026-09-04 に確認）

既定の経路エンジンは Valhalla で、こちらは `sign` として返してくる。
公開デモで東京駅 → 御殿場を引いた実際の応答:

```
{"instruction": "C1を直進です。",
 "sign": {"exit_branch_elements": [{"text": "C1"}]}}

{"instruction": "7番出口です。",
 "sign": {"exit_number_elements": [{"text": "7"}],
          "exit_name_elements": [{"text": "御殿場ＩＣ"}, {"text": "Gotemba"}]}}

{"instruction": "左方向です。その先138、山中湖/箱根方面です。",
 "sign": {"exit_branch_elements": [{"text": "138"}],
          "exit_toward_elements": [{"text": "山中湖"}, {"text": "箱根"}]}}
```

OSRM には無い **出口番号と出口名**まで取れる。
日本の高速道路の出口標識は緑地に番号を大きく出すので、それに倣って描く。

`exit_name_elements` は日本語と英語を並べて返す（「御殿場ＩＣ」と「Gotemba」）。
**日本語を優先し、日本語が無ければ先頭を使う**（英語しか無い地域のため）。

### 案内一覧（ターンリスト）

経路の全案内を順に並べたもの。出発前に道筋を確かめたり、
走行中に先の分岐を見たりする、カーナビの標準機能。

以前もリストはあったが、距離と文言だけの素っ気ないもので、
先頭 40 件で切れていた。次の 4 点を足した。

- **マニューバのアイコン**（左折・合流・ランプなどを一目で）
- **出発からの距離と通過予想時刻**。経路エンジンが持たせているのは
  「そこから次の案内まで」なので、手前までの合計を積み上げる
- **方面と路線番号**（OSM の destination / ref。無ければ出さない）
- **行を押すとその地点へ地図が飛ぶ**

積み上げの計算は `packages/navigation/src/maneuver-planner.ts` に置いた
（描画から切り離して測れるようにするため）。
1 つ壊れた案内があっても、その先の距離が NaN にならないことを測っている。

上限は 120 件。長距離では案内が数百件になるので、
超えたぶんは「ほか N 件の案内があります」と本数だけ示す。

### 経由地（先に寄ってから目的地へ）

市販カーナビの標準機能。出発地と目的地の間に、通る順に地点を挟む。
経路エンジンには既に `via` を渡す口があったので、BFF と UI を繋いだ。

実測（OSRM の公開デモ、東京駅 → 新宿駅、2026-09）:

| | 距離 | 案内の数 |
|---|---:|---:|
| 経由地なし | 8.07km | 15 |
| 経由地 1 か所（王子のあたり） | 13.18km | 23 |
| 経由地 2 か所 | 14.99km | 34 |

上限は 8 か所（BFF と UI の両方で止める）。
経路エンジンは地点が増えるほど時間がかかり、公開デモには
1 リクエスト/秒の制限もある。市販カーナビの経由地も 5 か所前後が普通。

読めない経由地（`via=abc` や範囲外の座標）は無かったことにして、
残りで経路を出す。1 つ壊れているだけで経路が出ないほうが困る。

**通過の判定が要る。** 経路を外れて再検索するとき、通過済みの経由地まで
渡してしまうと、一度通った場所へ引き返す経路が出る。
経由地を通り過ぎた直後の再検索で U ターンを指示されることになる。

判定は 60m 以内に近づいたら通過（`packages/navigation/src/via-points.ts`）。
経由地は目的地と違ってその建物に入る必要がなく、道の反対側を通ることもある。
片側 2 車線でも道幅は 15m 前後、これに測位の誤差（市街地で 10〜30m）を見込んだ。
**通過の記録は戻らない。** 戻せると、通り過ぎた先での再検索で引き返す。

**車線案内について、Valhalla は未対応。**
2026-09-04 に公開デモへ到達できたので確かめたところ、
一般道・高速道路のどちらの経路でも `lanes` は 0 件だった。
返ってこないものは解釈しようがないので、車線案内は OSRM のみ。
使いたい場合は `ROUTING_ENGINE=osrm`。

## 残っている宿題

### 未確認のもの

- 街路樹・信号が実機で出ることの確認（パーサ修正で取れるようになったはず）
- 道路・線路が実機で正しい位置に出ることの確認
- 「現在時刻に追従」を実機で 1 日通し、日没で星空と夜の環境光に切り替わることの確認
  （テストでは擬似時計で確認済み。実際の描画までは見ていない）
- 天候ごとの見え方を実機で確認（視程・日射・影はテストで測ったが、
  雨と雪のポストプロセスの見た目は目で見るしかない）
- Valhalla の車線情報。**2026-09-04 に公開デモへ到達できたが、
  一般道・高速道路のどちらの経路でも `lanes` は 0 件だった。**
  公開デモの版が返していないだけの可能性があるので、
  自前の Valhalla を新しい版で立てたら確認し直す。
  中身の形が分かるまで解釈はしない（誤った矢印は運転中に危ない）

### 実機ブラウザでの通し確認

型検査とテストでは見つからないものを拾うために、Chromium で開いて
コンソールエラー・未処理の例外・API の 500 を数える。

```
npm run measure:smoke      画面を開き、下シートのタブを一通り触る
npm run measure:startup    起動直後の取得の順序と本数を測る
```

この環境のブラウザは外部へ出られないので、地形・ベースマップ・
建物タイルはすべて `ERR_CONNECTION_RESET` になる。
**それでも画面が壊れないこと**を見るのが目的で、
見た目の良し悪しは判定しない。

2026-09-03 時点の結果: 問題なし。
地形が取れないときは楕円体へフォールバックし、UI は最後まで描かれる。

### まだ検証の網が掛かっていない場所

fuzz と実データの検証は、GIS・描画・ナビ・API・経路解析・AI のツール実行・
プロバイダの応答解析・建物の入れ替えまで一巡した。
プロバイダは擬似応答で検証したが、鍵が要るので実際の応答での確認はできていない。

### 軽量化（部品や精度を下げない方法）

道路の描画負荷は `npx tsx scripts/preprocessing/survey-roads.mts` で測れる。
浜松駅周辺 1km 四方の実測（2026-09）:

| | 形の数 | 頂点の目安 |
|---|---:|---:|
| 当初 | 3,972 | 51,622 |
| 細切れの道をつないだ後 | 3,631 | 50,892 |
| 外側線を幹線だけにした後 | 2,741 | 39,992 |

形 31% 減・頂点 23% 減。どちらも部品も精度も落としていない。
外側線の見直しは、むしろ実態に合わせた修正（住宅街の道に白線は無い）。

- [x] 上空では区画線を描かない（見えないものを描かない）。
      高度 800m を境に切り替える。範囲は同じなので取り直さず、
      手元のデータで組み直すだけ（通信も待ちも要らない）
- [x] 交差点の割り出しと形の組み立てを速くする（東京で 25.97ms → 13.07ms）。
      信号との突き合わせを 25m の格子にし、座標のキーから toFixed を外した。
      測り方: `npm run survey:road-timing`
- [x] タイルの取得順序の見直し。地形を待ってから建物を読んでいたのをやめ、
      並べて取りにいく形にした。実機ブラウザで地形サーバへ到達できない状態にすると、
      建物の tileset.json 要求が **13,360ms → 672ms**（20 分の 1）。
      測り方: `npx tsx scripts/measure/startup-requests.mts`
- [x] tileset.json の条件をクエリからパスへ移した。Cesium がクエリを子タイルへ
      引き継ぐため、bbox が変わるたびに同じタイルが別 URL になり、
      キャッシュが一切効いていなかった
- [ ] 道路・線路の描画をワーカーへ逃がす
      （**優先度は下がった。** 上の高速化で 1 フレームに収まったため。
      下の「正直に書いておく」を参照）

つなぎ処理で減ったのは 8% にとどまった。名前の一致を要求し、
分岐点ではつながないため。**これ以上つなぐと線形が嘘になる**ので広げない。

### Swift 移行を見据えた整理

- [x] `packages/shared/src/scene.ts` … 描画エンジン非依存の「形の記述」
- [x] `packages/gis/src/road-geometry.ts` … Cesium を import しない
- [x] 高架の組み立てを `SceneShape` を返す形に寄せた
      （`packages/gis/src/structure-geometry.ts`、679 行）。
      `elevated-structures.ts` は 877 → 220 行になり、
      残っているのは地形の標高取得と描画だけ。
- [x] `packages/gis` と `packages/shared` から Cesium 依存が完全に消えた
- [x] map-engine に残っていた「決め方」を shared / gis へ移した
      - `shared/weather.ts` … 天候ごとの視程・日射・影、霧の濃さ
      - `shared/building-colours.ts` … 用途ごとの色、高さによる明度
      - `gis/street-furniture-geometry.ts` … 距離に応じた樹冠の詳細度
      `map-engine/building-style.ts` は色を決めず、表を 3D Tiles の
      スタイル式に翻訳するだけになった。
      **スタイル式と色の関数が同じ色を出すことをテストで固定してある**
      （片方だけ直すと Web と Swift で街の色が変わるため）
- [x] `docs/architecture.md` に「Swift へ移すときの対応」の表を追加

### いま Cesium に依存しているのは packages/map-engine だけ

```
packages/gis/          OSM/PLATEAU の解釈、寸法の決定    … Cesium なし
packages/shared/       型と「形の記述」(scene.ts)        … Cesium なし
packages/map-engine/   形の記述を Cesium で描く          … ここだけ
```

Swift へ移すときは `map-engine` を置き換えれば、
寸法の決め方（何を描くか）はそのまま持っていける。

## これまでに片付いたこと（要点だけ）

| 課題 | 対処 | 効果 |
|---|---|---|
| 浜松で建物が二重に描かれる | near/far が同一四分木を返していた。`needsFarTileset` で遠景を作らない | タイル取得が半減 |
| 東京が重い | 端をかすめるだけの区まで開いていた。重なり面積順に上限まで | json 4.3→2.2MB、タイル 3,555→2,571 |
| 高架が重なる・積み上がる | 線路が 1 本ずつ別 way だった。縦につなぐ+横にまとめる+区間ごとに幅を測る | 重なり 110 組→9 組 |
| 高架に段差 | 高さの基準を桁下から路面へ | 1.2m の段が消えた |
| 橋が浮く | `layer=1` が水路との上下関係だった | 浜松の道路橋 56 本すべてが該当 |
| 建物のスタイルが当たらない | `defined()` はスタイル式に無い / `${['bldg:usage']}` は黙って undefined | 遠景の色が初めて付いた |
| 3D モデルがチカチカする | 「先に消してから作る」を「作ってから消す」へ（建物・高架・街路樹） | 空白の数秒が無くなった |
| 信号・街路樹が出ない | OSM XML パーサの先読みが成立せずノードが 0 件 | ノードが取れるようになった |
| Cesium アセットが大きい | GoogleEarth/I3S/Splats/zip/waterNormals を配布から除外 | 5.9→4.7MB |
| 柱が多すぎる | 距離に応じて 2 の冪で間引く | 柱 38% 削減 |
| 水路判定が遅い | 矩形の早期棄却 + WeakMap キャッシュ | 154ms→49ms |
| 高架でない所が高架になる | `layer>0` だけで判定していた。トンネル除外 + 長さ条件 + 歩行者用は bridge 必須 | 東京で誤り 254 本→0 |
| 縮小すると日本地図が消える | 地理院タイルに z=0/1 が無いのに `minimumLevel` 未指定だった | 引いても地球に絵が貼られる |
| 読み込み中に操作すると落ちる | 破棄後の scene に触っていた。`liveScene()` で毎回確かめる | 例外が出なくなった |
| 極端なタグでブラウザが固まる | `tracks=1000000000` で線路を 10 億本組もうとしていた | 上限を掛けた |
| 検索結果が入力と食い違う | 通信中に入力が変わると古い結果が新しい結果を上書き | 古い検索を捨てる |
| 引数なしの API 要求が通る | `Number(null)` が 0 なので「大西洋の座標」として受けていた | 検証を shared に集約 |
| 線路や道がどこにも描かれない | 地表側と高架側で判定が食い違っていた | 東京で 136 本が復活 |
| 経路エンジンの応答欠けで英語の内部エラーが出る | 必須のはずの配列が undefined で来る 7 通りを塞ぐ | 日本語の案内に統一 |
| 複数レグの経路が日本から飛ぶ | polyline の文字列を連結していた（差分符号なので不正） | 座標から符号化し直す |
| 現在時刻に追従すると発熱する | 時計を進めると requestRenderMode が無効になっていた | 描画 60/秒→1/分 |
| 追従中に夜になっても昼のまま | 夜の補正と星空を最初の 1 回しか適用していなかった | 日没で切り替わる |
| AI が地図を壊せる | 俯角 -400 度・高度 0・負の半径がそのまま通っていた | 数値も範囲を検証 |
| Gemini の鍵が URL に載る | `?key=` から `x-goog-api-key` ヘッダへ | ログに鍵が残らない |
| 地図の状態が未検証で AI に渡る | NaN の座標・改行入りの都市名が素通り | `readLatLng` で検証 |
| 建物の入れ替え中に画面を離れると落ちる | 最大 8 秒待つ間に viewer が破棄される経路が 3 か所 | `liveScene` で塞いだ |
| 高架へ上がる手段が無い | 階段を接続先の路面高さから組み立てる | 浜松で 5 本、東京で 11 本 |
| 盛土に柱が並ぶ | `embankment=yes` を無視して高架橋にしていた | 東京で形 6,291→4,218 |
| 高架の手前で道が途切れる | 端点を共有する道を標準の勾配で上げる | 浜松 91 本・東京 70 本 |
| 浜松の高架でエラー | 取得に合計の締め切りが無く 80 秒かかっていた | 28 秒・構造物 408 件 |
| 街路樹が必ず 0 件 | ここだけ OSM 本体への切り替えが無かった | 切り替えを追加 |
| 木が棒付きキャンディ | 幹 1 本 + 球 1 個だった | 幹 + 樹冠 5 個・樹形 4 種 |
| 信号が信号に見えない | 柱だけ・全部が真北向き | アーム + 実寸 + 道の向き |
| 信号の柱が道の真ん中 | OSM のノードは車道の中心線上にある | 路肩へ寄せる（30/30 基） |
| 区画線が交差点を突っ切る | 交差点で切っていなかった | 288 か所で分断・停止線 150 本 |
| 移動しても施設が出ない | カメラの移動を見ていなかった | 400m/500m で追従 |
| 時間帯がリアルじゃない | 5:30/18:30 の固定閾値。冬の 17 時が昼だった | 太陽高度で連続的に |
| 天候を選んでも変わらない | 霧の濃さを少し動かすだけだった | 視程・日射・影の 3 つ |
| 見え方が都市ごとの決め打ち | 東京は必ずテクスチャ付きだった | 3 通りから選べる |
| 建物タイルにキャッシュが効かない | Cesium が tileset.json のクエリを子へ引き継いでいた | 条件をパスへ移した |
| 起動しても街がなかなか出ない | 地形を待ってから建物を読んでいた | 13,360ms → 672ms |
| 車線案内が無い | カーナビにあって、これに無かった | OSM の turn:lanes から表示 |
| 方面案内が無い | 分岐で「どちらが目的の方向か」が分からない | OSM の destination から表示 |
| 案内一覧が素っ気ない | 距離と文言だけ、先頭 40 件で打ち切り | アイコン・累積距離・通過時刻・方面 |
| 線路が埋まる | 高架の上に軌道が無かった | 浜松の線路 55 本が見えるように |
| 線路が波打つ・地面に沈む | 100m 格子の標高をそのまま当てていた | 平して路盤に食い込ませた |
| 線路がリアルでない | レールが浮いた棒だった | 枕木・架線柱・軌間の作り分け |
| 経由地を指定できない | 経路エンジンに口はあったが繋がっていなかった | 8 か所まで、順に通る |
| 移動してもすぐ表示されない | カメラの移動を**操作の始まり**で代用していた。指を置いた瞬間に判定するので、ドラッグしても離しても何も起きなかった | `camera.moveEnd` と `camera.changed` を見る |
| 近づくと建物が消える | 市域の縁で、同じ範囲のタイルセットを 0.5 秒ごとに作り直していた（判定は収める前、要求は収めたあとの値で行っていた） | 同じ範囲なら読み直さない |
| 高架に降りても軌道が出ない | 軌道の有無はカメラ高度で決まるのに、描画の鍵に入っていなかった | 鍵に混ぜ、手元のデータで組み直す |
| 空振りすると二度と読まなくなる | 「この範囲に無い」で戻っていたため、追従の起点（中心）も控えられなかった | 取り寄せに失敗したときだけ戻る |
| 同じ範囲を二重に取り寄せる | 二重起動の門を `useState` → `useEffect` → ref で作っていた | ref に直接書いてその場で閉める |

### 正直に書いておく

- 500m 格子への丸めは、**一方向に移動し続ける場合は取り直しの回数が変わらない。**
  同じ場所を行き来するときにだけ効く。
- Cesium 本体の JS は生 3.9MB だが gzip で 1.0MB。
  ダウンロード量は妥当で、重さの主因は実行時にある。
- **ワーカーへ逃がす件は、測ってみたら急ぐ理由が無くなった。**
  逃がす価値があるのは主スレッドを 1 フレーム（16.7ms）以上止める処理だけ。
  高速化の前は東京で 25.97ms あったが、いまは 13.07ms で収まっている。
  しかも `SceneShape` は 8,600 個・102,300 頂点あり、
  ワーカーとの受け渡し（構造化複製）のほうが高くつく可能性がある。
  やるとしたら、まず複製のコストを測ってから決める。
- 起動の測定は SwiftShader（ソフトウェア描画）で行っているので、
  FPS の値は実機の指標にならない。**要求の順序と時刻だけを見ている。**
  この環境ではブラウザから外部へ出られないため、
  地形とベースマップのタイル本体は「応答なし」になる。
