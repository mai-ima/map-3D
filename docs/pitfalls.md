# 落とし穴の記録

一度はまって、原因の特定に時間がかかったもの。
どれも「見た目では気づけない」か「黙って失敗する」たぐいで、
知らずに触ると同じところで止まる。

該当する領域を触る前に、その節を読むこと。

## Cesium

### PolylineVolumeGeometry の断面は外接矩形で正規化される

`PolylineVolumeGeometry` に渡した断面（`shapePositions`）は、
内部の `convertShapeTo3D` が **x も y も外接矩形のぶんだけ引く。**
つまり断面に書いた y の絶対値は無視され、
**中心線の高さから必ず上へ**押し出される。

```
node_modules/cesium/Build/CesiumUnminified/Workers/chunk-FBP4DUQJ.js
```

「梁を中心線の下にぶら下げよう」として断面に負の y を書いても、
そのぶん上にずれるだけで、見た目からは何も分からない。

**書き方の決まり:**
- 断面は必ず **y = 0 を下端**として書く
- 中心線には、その部材の **下面**の高さを渡す

`packages/map-engine/src/elevated-structures.ts` はこの規約で統一してある。
検証は `__tests__/elevated-structures.test.ts` が頂点座標を実測している。

### Cesium3DTileStyle の式に `defined()` は無い

スタイル式で使えるのは `isNaN()` / `isFinite()` だけ。
`defined()` を書くと式全体が失敗し、**スタイルが丸ごと当たらない。**
例外は出ず、ただ色が付かないだけなので気づきにくい。

これが原因で、遠景タイルセットのスタイルが全都市で一度も適用されていなかった。

### コロンを含む属性は `${feature['...']}` でしか読めない

```
${bldg:usage}              パースエラー（Unexpected ":" at character 8）
${['bldg:usage']}          パースは通るが常に undefined（黙って失敗する）
${feature['bldg:usage']}   正しい
```

2 番目が最も危険。エラーが出ないまま全条件が外れる。
`packages/map-engine/src/building-style.ts` では属性名を定数にまとめ、
書き間違いが一箇所で済むようにしてある。

### `color('#rrggbb') * 0.96` はアルファまで掛かる

明度を落とすつもりで掛け算すると、アルファも 0.96 になって半透明になる。
建物が薄くなり、奥の建物が透けて見える。

```
vec4(r * S, g * S, b * S, 1.0)   … アルファは明示的に 1.0
```

### `Primitive` は add した直後には何も描かれない

`asynchronous: true`（既定）の `Primitive` はワーカーで頂点を組むので、
`scene.primitives.add()` した直後は `ready` が false で、まだ何も出ていない。

古いものを先に消して新しいものを add すると、
組み上がるまでの数秒間そこが空白になる。これがちらつきの正体。

**新しいものが `ready` になってから古いものを消す。**
`packages/map-engine/src/primitive-swap.ts` の `waitForPrimitives` を使う。
`requestRenderMode` では描画が走らないと組み立ても進まないので、
待っている間はこちらから `scene.requestRender()` を呼ぶ必要がある。

### 地表に貼る帯は、細いものを面で描くと消える

区画線の実寸は 0.15m。これを `CorridorGeometry` の面として地表に貼ると、
少し離れただけで 1 画素を割って見えなくなる。

実際の地図やカーナビは、区画線を「画面上の太さ」で描いている。
`packages/map-engine/src/scene-renderer.ts` では 0.5m を境に、
太いものは面（`CorridorGeometry` + `GroundPrimitive`）、
細いものは線（`GroundPolylineGeometry` + `GroundPolylinePrimitive`）で描く。

破線の刻みも同じ理由で画素基準になる（`PolylineDash` の `dashLength` は
画素単位で、メートルでは指定できない）。実寸で刻めるのは横断歩道のような
太い縞だけ。位置と本数は実データどおりで、近似しているのは刻みの細かさだけ。

### `geometricError: 1e+100` は必ずしも「全部読む」ではない

台東区の tileset.json は根の `geometricError` が `1e+100` になっている。
一見「打ち切りが効かず全タイルを読む」ように見えるが、
深さ 0〜14 は子を 1 つだけ持つ空の入れ物で、
深さ 15 以降は正常な値（64 → 32 → 16 → 8）に戻る。
SSE による打ち切りはちゃんと効いている。

（当初これを「無条件に 797 タイルを読む」と誤って判断した。
 実際に json を辿って数えるまで結論を出さないこと。）

## 数値と反復

### 距離で刻むループは、進まない刻み幅で止まらなくなる

経路を「線 8m・空き 12m」で刻む処理で、無限ループを作って
テストが 120 秒でタイムアウトした。

```
const remaining = inLine ? on - phase : period - phase;
const step = Math.min(remaining, segment - cursor);
cursor += step;   // step が 0 だと永久に進まない
```

位相がちょうど境目に乗ると `remaining` が 0 になり、`cursor` が
進まないまま回り続ける。浮動小数の計算では「ちょうど乗る」ことが起きる。

**距離を足して進めるループには、必ず前へ進む最小の刻みを入れる。**

```
const remaining = Math.max(1e-6, inLine ? on - phase : period - phase);
```

### 緯度経度の引き算は割り切れない

`34.71 - 34.7` は `0.00999999999999801` になる。
格子点ちょうどを指しても最後の桁がずれるので、
座標から求めた値を厳密な一致で検証してはいけない。
許容誤差を決めて比較する（標高なら 1mm で十分）。

## OpenStreetMap

### `bridge=yes` + `layer=1` は「水路の上」かもしれない

`layer` を「高架の階数」と解釈すると、川に架かるだけの普通の橋が
路面から 4〜5m 浮く。

浜松の実測（2026-08）: 道路橋 56 本のうち **56 本すべてが水路を渡る橋**だった。
`layer=1` は道路ではなく水路との上下関係を表していた。

対処: Overpass のクエリに水路（`waterway=river|stream|canal|drain|ditch`）を含め、
経路が水路と交差するかで桁下高を決める。
`packages/gis/src/structures.ts` の `crossesWaterway` / `deckHeightOf`。

桁下高の実際の値:
| | 水路の上 | 道路・線路の上 |
|---|---|---|
| 道路 | 1.2m | 5.6m |
| 歩道 | 1.6m | 5.6m |
| 鉄道 | 1.8m | 6.5m |

### 線路は 1 本ずつ別の way になっている

複線・多線区間でも `railway=rail` の way は線路 1 本ごとに分かれている。
そのまま構造物として扱うと、高架が何十本も重なって描かれる。

浜松の実測: 新幹線の高架部で **15 本**、軌道中心間隔 3.8〜4.3m
（日本の標準は 4.1m）。

対処: `packages/gis/src/structure-merge.ts`
1. 端点が近いものを縦につなぐ（`stitchStructures`）
2. 平行に走るものを横にまとめる（`mergeParallel`、Union-Find）
3. 基準線に沿って幅を測り、変わるところで区間に分ける（`segmentByWidth`）

これで重なりが 110 組から 9 組に減った。

### `<node>` の解析で先読みを使うと 1 件も取れない

以前のパーサは「次の要素が始まるところまで」を先読みで探していた。

```
/<node\s+([^>]*?)(\/)?>([\s\S]*?)(?:<\/node>)?(?=<node|<way|<relation|$)/g
```

実際の XML は `</node>` と次の `<node>` の間に改行と字下げが入るため、
この先読みが一度も成立せず、**ノードを 1 件も取り出せていなかった。**
信号・横断歩道・街路樹はすべてノードなので、これらが丸ごと落ちていた。

閉じタグそのものを終端にすれば、間に何が入っていても取れる。

```
/<node\b([^>]*?)(?:\/>|>([\s\S]*?)<\/node>)/g
```

（`packages/gis/src/osm-api.ts`。`parseOsmXml` は検証のために export してある。）

### 車線数の補完値から幅を逆算しない

OSM の道路タグの充足率は低い。浜松駅周辺 3km 四方の実測（2026-08）:

| タグ | 入っている割合 |
|---|---|
| `lanes` | 7% |
| `maxspeed` | 3% |
| `width` | 0% |

足りないぶんは道路構造令の標準値で補うが、
**補完した車線数からさらに幅を計算してはいけない。**
生活道路も 3 級道路もどちらも「対面 2 車線」に補完されるので、
逆算するとどちらも同じ 7m になり、道の格の違いが消える。

幅は「実データ → 実データの車線数 → 種別ごとの標準幅」の順で決める。
（`packages/gis/src/road-geometry.ts` の `roadWidthOf`。
 この誤りはテストが検出した。）

### 速度制限は推測しない

`maxspeed` が入っていないときは表示しない。
種別から推測すると、実際とは違う数字を標識のように見せることになる。
`JP:urban` のような記号も数値ではないので採らない。

## PLATEAU

### 神戸市には 3D 都市モデルが無い

datacatalog に建物モデルが存在しない。対応都市から外し、
LOD2（テクスチャあり）が揃っている **姫路市（28201）** に差し替えた。
対応都市を増やすときは、まず datacatalog に実データがあるか確かめる。

### near と far が同じ四分木を指すことがある

浜松では近景用と遠景用のタイルセットが同一の四分木を返していた。
結果、同じ建物が二重に描かれ、タイルの取得も 2 倍になっていた。

`packages/map-engine/src/buildings.ts` の `needsFarTileset(city)` で、
近景がすでに直接タイルセットを指している都市では遠景を作らない。

### 端をかすめるだけの区まで開いてしまう

東京は 8 区にまたがるが、そのうち 4 区は表示範囲の端をかすめるだけで、
それが総タイル数の半分を占めていた。

`app/api/tileset/route.ts` で、重なり **面積**の大きい順に並べ、
上限（近景 5・遠景 10）まで残す。
これで tileset.json が 4.3MB → 2.2MB、タイル数が 3,555 → 2,571 になった。

## 座標と幾何

### 方位角の計算に `cos(緯度)` を忘れない

経度 1 度あたりの距離は緯度によって変わる。
これを忘れると柱が構造物に対して斜めを向く。
北緯 34.7 度では約 18% ずれ、45 度方向の柱の見付けが √2 倍に膨らむ。

検証: `elevated-structures.test.ts` の
「斜めに走る高架でも柱が構造と平行に立つ」が実際に見付け幅を測っている。

### 高さの基準は「路面」から下へ取る

桁下を基準にすると、同じ路線でも構造形式が変わる接続部で路面に段差ができる
（実際に 1.2m の段ができていた）。

```
deckTop    = 地盤 + deckHeight   路面（軌道面・車道面）
slabBottom = deckTop - 版厚      床版の下面 = 梁の上面
beamBottom = slabBottom - 梁高   梁下。柱の頭でもある
```

さらに、つながっている構造物どうしで路面高を揃える（`alignDeckHeights`）。
