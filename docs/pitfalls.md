# 落とし穴の記録

一度はまって、原因の特定に時間がかかったもの。
どれも「見た目では気づけない」か「黙って失敗する」たぐいで、
知らずに触ると同じところで止まる。

該当する領域を触る前に、その節を読むこと。

---

## Cesium

### PolylineVolumeGeometry の断面は外接矩形で正規化される

`PolylineVolumeGeometry` に渡した断面（`shapePositions`）は、
内部の `convertShapeTo3D` が **x も y も外接矩形のぶんだけ引く。**
つまり断面に書いた y の絶対値は無視され、
**中心線の高さから必ず上へ**押し出される。

```
node_modules/cesium/Build/CesiumUnminified/Workers/chunk-FBP4DUQJ.js
```

「梁を中心線の下にぶら下げよう」として断面に負の y を書いても、
そのぶん上にずれるだけで、見た目からは何も分からない。

**書き方の決まり:**
- 断面は必ず **y = 0 を下端**として書く
- 中心線には、その部材の **下面**の高さを渡す

`packages/map-engine/src/elevated-structures.ts` はこの規約で統一してある。
検証は `__tests__/elevated-structures.test.ts` が頂点座標を実測している。

### Cesium3DTileStyle の式に `defined()` は無い

スタイル式で使えるのは `isNaN()` / `isFinite()` だけ。
`defined()` を書くと式全体が失敗し、**スタイルが丸ごと当たらない。**
例外は出ず、ただ色が付かないだけなので気づきにくい。

これが原因で、遠景タイルセットのスタイルが全都市で一度も適用されていなかった。

### コロンを含む属性は `${feature['...']}` でしか読めない

```
${bldg:usage}              パースエラー（Unexpected ":" at character 8）
${['bldg:usage']}          パースは通るが常に undefined（黙って失敗する）
${feature['bldg:usage']}   正しい
```

2 番目が最も危険。エラーが出ないまま全条件が外れる。
`packages/map-engine/src/building-style.ts` では属性名を定数にまとめ、
書き間違いが一箇所で済むようにしてある。

### `color('#rrggbb') * 0.96` はアルファまで掛かる

明度を落とすつもりで掛け算すると、アルファも 0.96 になって半透明になる。
建物が薄くなり、奥の建物が透けて見える。

```
vec4(r * S, g * S, b * S, 1.0)   … アルファは明示的に 1.0
```

### `Primitive` は add した直後には何も描かれない

`asynchronous: true`（既定）の `Primitive` はワーカーで頂点を組むので、
`scene.primitives.add()` した直後は `ready` が false で、まだ何も出ていない。

古いものを先に消して新しいものを add すると、
組み上がるまでの数秒間そこが空白になる。これがちらつきの正体。

**新しいものが `ready` になってから古いものを消す。**
`packages/map-engine/src/primitive-swap.ts` の `waitForPrimitives` を使う。
`requestRenderMode` では描画が走らないと組み立ても進まないので、
待っている間はこちらから `scene.requestRender()` を呼ぶ必要がある。

### 地表に貼る帯は、細いものを面で描くと消える

区画線の実寸は 0.15m。これを `CorridorGeometry` の面として地表に貼ると、
少し離れただけで 1 画素を割って見えなくなる。

実際の地図やカーナビは、区画線を「画面上の太さ」で描いている。
`packages/map-engine/src/scene-renderer.ts` では 0.5m を境に、
太いものは面（`CorridorGeometry` + `GroundPrimitive`）、
細いものは線（`GroundPolylineGeometry` + `GroundPolylinePrimitive`）で描く。

破線の刻みも同じ理由で画素基準になる（`PolylineDash` の `dashLength` は
画素単位で、メートルでは指定できない）。実寸で刻めるのは横断歩道のような
太い縞だけ。位置と本数は実データどおりで、近似しているのは刻みの細かさだけ。

### 地理院タイルにはズーム 0 と 1 が無い

`minimumLevel` を指定しないと、Cesium はズーム 0 から読もうとして 404 になる。
その結果、引いた状態で地球に何も貼られず、**縮小すると日本地図が消えたように見える。**
エラーは画面に出ないので、黒いことしか分からない。

実測（2026-09、cyberjapandata.gsi.go.jp）:

| レイヤ | 提供ズーム | 範囲 |
|---|---|---|
| seamlessphoto / std / pale | 2〜18 | 世界中（北米 5/7/12・欧州 5/16/10・豪州 5/28/18 で 200 を確認） |
| blank | 5〜14 | 日本国内のみ（国外は 404） |

`minimumLevel` を上げるほど全球を覆う枚数が増える（4^n 枚）。
ズーム 2 なら 16 枚なので、起動の負担にはならない。
国内にしか無いレイヤは `rectangle` で範囲を区切り、無駄な 404 を出さない。

### 描画距離は毎フレーム合わせる

`frustum.far` の更新を 0.5 秒間隔の監視処理に相乗りさせていたため、
慣性の効いたズームで高度が一気に変わると far が追いつかず、
地球がクリップ面の外に出て一瞬消えていた。

far の計算は数回の乗除算なので毎フレームでよい。
一方、上限を超えたカメラの引き戻し（`setView`）は毎フレームやると
カメラ操作と競合するので、監視と同じ間隔のままにする。

### `geometricError: 1e+100` は必ずしも「全部読む」ではない

台東区の tileset.json は根の `geometricError` が `1e+100` になっている。
一見「打ち切りが効かず全タイルを読む」ように見えるが、
深さ 0〜14 は子を 1 つだけ持つ空の入れ物で、
深さ 15 以降は正常な値（64 → 32 → 16 → 8）に戻る。
SSE による打ち切りはちゃんと効いている。

（当初これを「無条件に 797 タイルを読む」と誤って判断した。
 実際に json を辿って数えるまで結論を出さないこと。）

### 時計を進めると `requestRenderMode` が効かなくなる

`clock.shouldAnimate = true` にすると、時刻が変わるたびに再描画が要求される
（`Scene.maximumRenderTimeChange` の既定は 0 で、どんな変化でも描き直す）。
静止中に描かないという省電力の仕組みが丸ごと無効になり、
「現在時刻に追従」を選んだだけで iPhone が発熱し続ける。

太陽は 1 分で 0.25 度しか動かない。時計は止めたまま、
こちらから 1 分ごとに `currentTime` を入れ直せば、
見た目は同じで描画は 1 分に 1 回で済む。

**そして「一度だけ適用して終わり」にしない。**
以前は追従を入れた瞬間の 1 回しか適用しておらず、
昼に追従を入れたまま夜になっても環境光は昼のまま、星も出なかった。
太陽の位置は Cesium が時刻から計算してくれるが、
夜の補正・星空・環境光は自分で入れ直さないと切り替わらない。

### 精細度を「読み込み待ち」に連動させると振動する

読み込み待ちのタイルが増えたら精細度を落とす、という自己調整を入れたら、
いつまでも読み込みが終わらなくなった。

精細度（`maximumScreenSpaceError`）を変えると Cesium はタイルツリーを
**再評価する**。すると次のループに入る。

```
待ちが増える → 粗くする → タイルが破棄されて待ちが減る
            → 細かくする → また待ちが増える → …
```

待ち行列との連動をやめ、**カメラ高度だけで決める**形にした。
そのうえで、はっきり差が出たとき（20% 以上）に、
一定の間隔を空けてしか反映しない（`SSE_CHANGE_INTERVAL_MS`）。

一般化すると、**「結果が入力に返ってくる量」を制御の入力にしてはいけない。**
入力にしてよいのは、制御の結果で変わらないもの（カメラの高度・端末の性能）だけ。

### FPS 0 は異常ではない

`requestRenderMode` を有効にしていると、静止中は 1 フレームも描かない。
診断パネルの FPS が 0 になるのはそのためで、正常な状態である。

区別が付かないと「固まった」と誤診して、効かない対策を重ねることになる
（実際にそうなった）。診断パネルでは `idle` として別に表示している。

```ts
idle: this.fps === 0 && this.viewer.scene.requestRenderMode && !this.navigating
```

### iOS の `gl.flush()` は、入れる場所を間違えると逆効果

WebKit の推奨は「1 フレームに大量の描画コマンドを積むな、
`flush()` で**途中で**分割せよ」。
これを Cesium の `postRender`（フレーム描画の**最後**）で呼んでも、
コマンドの分割にならない。ブラウザは元々フレーム末尾で暗黙に flush するので、
追加の flush はパイプラインをストールさせるだけだった。

**入れて、測って、外した。** 詳しくは `docs/research.md` の
「iOS / WebKit の WebGL 制約」を参照。

根本の対処は「描く量そのものを減らす」ことで、
起動直後に都道府県まるごとの tileset を展開していた件を直したのが
最も効いた。

## 時間帯と天候

### 固定の時刻で昼夜を分けると、季節が逆になる

以前は「5:30 より前と 18:30 より後は夜」という閾値で切り替えていた。
日本の日の出・日の入りは季節で 2 時間半動くので、これは実際とずれる。

```
東京（国立天文台 暦計算室）
  夏至  日の出 04:25  日の入り 19:00
  冬至  日の出 06:47  日の入り 16:32
```

固定の閾値だと **12 月の 17 時が「昼」、6 月の 5 時が「夜」** になる。
どちらも実際とは逆で、これが「時間帯がリアルじゃない」の正体だった。

太陽高度は暦の計算で決まる値なので、創作ではない。
`packages/shared/src/sun.ts` に NOAA Solar Calculator の式
（Jean Meeus, *Astronomical Algorithms* の簡略式）を置いた。
Cesium を import しないので、そのまま Swift へ持っていける。

**明るさは段で切り替えない。** 「夜なら 1.4、昼なら 0.85」のように
分けると、日の入りの瞬間に街全体の明るさが飛ぶ。
`daylightStrength()`（0〜1）を掛けて連続的に変える。

### 太陽高度は見ている場所で変わる

同じ 19 時でも、夏至の日の入りは根室 19:01・那覇 19:24 で 23 分違う。
カメラが都市をまたいだら太陽高度を計算し直す
（`EnvironmentController.setViewpoint`）。

ただしカメラは 0.5 秒ごとに動く。そのたびに空を塗り直すのは無駄なので、
**0.5 度（約 55km）以上離れたときだけ**入れ直す。
数十 km では太陽高度は 0.5 度も変わらない。

### 天候は「霧の濃さ」だけでは伝わらない

以前は霧の density と空の彩度をわずかに動かすだけで、
晴れと雨を選び分けても街の見え方がほとんど変わらなかった。
「天候システムが意味ない」と言われたのはこれ。

天候で実際に変わるのは 3 つある。

| | 視程 | 直射日光 | 影 |
|---|---|---|---|
| 晴れ | 30km | 1.0 | できる |
| 曇り | 14km | 0.45 | できない |
| 雨 | 6km | 0.22 | できない |
| 雪 | 2.5km | 0.3 | できない |
| 霧 | 0.7km | 0.35 | できない |

視程は気象庁の視程階級に合わせた
（霧の定義がそもそも「視程 1km 未満」）。
日射の割合は全天日射量と雲量の関係の実測値による。
**影の有無が最も効く。** 曇りの日に建物の影が地面に落ちていると、
どれだけ空を灰色にしても晴れにしか見えない。

Cesium の `fog.density` は「その距離で霧に沈む」という単位ではないが、
実測すると density × 視程 ≈ 6 で一定になる。
視程を先に決めて density を逆算すれば、表に書いた値がそのまま意味を持つ。

### 天候を変えたら、時刻の明るさを入れ直す

`applyWeather()` が日射と影を上書きするので、その中で `applyTime()` を
呼び直さないと、夜に天候を選んだ瞬間だけ昼の明るさに戻る。
時刻と天候は掛け算で効くもので、独立に設定できるものではない。

## 数値と反復

### 距離で刻むループは、進まない刻み幅で止まらなくなる

経路を「線 8m・空き 12m」で刻む処理で、無限ループを作って
テストが 120 秒でタイムアウトした。

```
const remaining = inLine ? on - phase : period - phase;
const step = Math.min(remaining, segment - cursor);
cursor += step;   // step が 0 だと永久に進まない
```

位相がちょうど境目に乗ると `remaining` が 0 になり、`cursor` が
進まないまま回り続ける。浮動小数の計算では「ちょうど乗る」ことが起きる。

**距離を足して進めるループには、必ず前へ進む最小の刻みを入れる。**

```
const remaining = Math.max(1e-6, inLine ? on - phase : period - phase);
```

### 数を比べるときは、同じ条件で取ったものどうしで比べる

「道路が 533 本から 583 本に増えた」と報告して、直後に訂正した。
片方は絞り込み後の数、もう片方は絞り込み前の数で、
**比較対象が違っていた。**

改善を数で示すときは、
**同じ範囲・同じ絞り込み・同じ時点**で取った値を並べる。
測る道具（`npm run survey:*`）を用意してあるのは、
毎回同じ条件で取れるようにするため。

「軽くなった」「増えた」を言う前に、比べている 2 つが本当に同じ条件かを見る。

### 緯度経度の引き算は割り切れない

`34.71 - 34.7` は `0.00999999999999801` になる。
格子点ちょうどを指しても最後の桁がずれるので、
座標から求めた値を厳密な一致で検証してはいけない。
許容誤差を決めて比較する（標高なら 1mm で十分）。

## OpenStreetMap

### `bridge=yes` + `layer=1` は「水路の上」かもしれない

`layer` を「高架の階数」と解釈すると、川に架かるだけの普通の橋が
路面から 4〜5m 浮く。

浜松の実測（2026-08）: 道路橋 56 本のうち **56 本すべてが水路を渡る橋**だった。
`layer=1` は道路ではなく水路との上下関係を表していた。

対処: Overpass のクエリに水路（`waterway=river|stream|canal|drain|ditch`）を含め、
経路が水路と交差するかで桁下高を決める。
`packages/gis/src/structures.ts` の `crossesWaterway` / `deckHeightOf`。

桁下高の実際の値:
| | 水路の上 | 道路・線路の上 |
|---|---|---|
| 道路 | 1.2m | 5.6m |
| 歩道 | 1.6m | 5.6m |
| 鉄道 | 1.8m | 6.5m |

### 高架の上に軌道を敷き忘れると、線路が「埋まって」見える

高架橋は床版・縦梁・柱・防音壁で組んでいたが、**その上に軌道が無かった。**
床版だけが宙に浮いていて、線路がどこにも見えない。

これが「線路が埋まる」の正体だった。
浜松駅周辺 1km 四方の実測（2026-09-04）:

```
線路 55 本 = 地表 0 / 高架 55 / 地下 0
```

浜松駅・遠州鉄道はすべて高架化されているので、**線路が 1 本も見えていなかった。**
東京は地表 68 / 高架 197 / 地下 99 で、高架のぶんが同じ状態だった。

高架橋の軌道はスラブ軌道が標準（新幹線と都市部の高架）。
バラスト軌道と違って道床が無く、コンクリートの軌道スラブにレールを直結する。
保守が要らないので高架では必ずこちらになる。

出典: 鉄道構造物等設計標準（軌道構造）。
軌道スラブ A 形 4,930 × 2,340 × 190mm、軌間は在来線 1,067mm / 新幹線 1,435mm。

足しても負荷はほとんど変わらない（実測）:

| | 形の数 | 頂点 |
|---|---:|---:|
| 浜松 軌道なし | 6,598 | 214,908 |
| 浜松 軌道あり | 6,763 | 228,996 |
| 東京 軌道なし | 6,057 | 227,316 |
| 東京 軌道あり | 6,543 | 243,492 |

### 地表の線路は、地形の標高をそのまま当てると埋まるし波打つ

道路は `GroundPrimitive`（地形にクランプ）で描くので絶対に埋まらないが、
線路は立体なので絶対高さで置く。その高さを 100m 格子の標高から
補間していたため、実際の地面とずれると沈む。

東京駅周辺の線路上 12 点で、国土地理院の標高 API と
100m 格子の双線形補間を比べた（2026-09-04）:

```
差の絶対値の中央値 0.08m / 最大 0.25m
格子のほうが高い（＝線路が埋まる）点 6 / 12
```

道床の高さは 0.4m しかないので、0.25m 沈むと 6 割が地面に入る。
**東京駅周辺は標高 3m 前後の平地でこれ**なので、起伏があればもっと沈む。

対処は 2 つ。

1. **道床を路盤に食い込ませる**（`BALLAST_EMBED_M = 0.15`）。
   バラストは路盤の上に載っているのではなく、掘り下げたところに入っている。
   下端を沈めれば、地形が多少高く出ても上面が地表に残る
2. **高さを敷設に合わせて平す**（`levelRailHeights`）。
   標高をそのまま頂点に当てると、線路が地面の凹凸をなぞって波打つ。
   実物の線路は路盤で平されていて、勾配は連続で緩やかに変わる。
   移動平均をかけたうえで、縦断勾配の上限（本線 35‰、
   鉄道に関する技術上の基準を定める省令の解釈基準 第 15 条）を守らせる

### 枕木は「近くの線路」にだけ描く

枕木は 0.54m 間隔（在来線 1 級線で 1km あたり 1,850 本）。
範囲内すべての線路に描くと、東京駅周辺 1km 四方で
**13,397 個・頂点 339,448** になった。道路全体が 102,300 頂点なので、
線路だけでその 3 倍を使うことになる。

絞り方は 2 段。

- カメラの高さで刻み幅を変える（60m 未満は実寸、160m 未満は 2 本に 1 本、
  それ以上は描かない）。**間引きは 2 の冪で**
- **カメラから 120m 以内の線路にだけ描く。**
  東京駅は 20 面 20 線で密集しており、200m だと視界の外まで持ってしまう

3,214 個・頂点 95,056 に収まった（76% 減）。
どの線路が近いかは描画側にしか分からないので、
その振り分けは `map-engine` が行う（寸法の決め方は GIS 側のまま）。

### 線路は 1 本ずつ別の way になっている

複線・多線区間でも `railway=rail` の way は線路 1 本ごとに分かれている。
そのまま構造物として扱うと、高架が何十本も重なって描かれる。

浜松の実測: 新幹線の高架部で **15 本**、軌道中心間隔 3.8〜4.3m
（日本の標準は 4.1m）。

対処: `packages/gis/src/structure-merge.ts`
1. 端点が近いものを縦につなぐ（`stitchStructures`）
2. 平行に走るものを横にまとめる（`mergeParallel`、Union-Find）
3. 基準線に沿って幅を測り、変わるところで区間に分ける（`segmentByWidth`）

これで重なりが 110 組から 9 組に減った。

### `<node>` の解析で先読みを使うと 1 件も取れない

以前のパーサは「次の要素が始まるところまで」を先読みで探していた。

```
/<node\s+([^>]*?)(\/)?>([\s\S]*?)(?:<\/node>)?(?=<node|<way|<relation|$)/g
```

実際の XML は `</node>` と次の `<node>` の間に改行と字下げが入るため、
この先読みが一度も成立せず、**ノードを 1 件も取り出せていなかった。**
信号・横断歩道・街路樹はすべてノードなので、これらが丸ごと落ちていた。

閉じタグそのものを終端にすれば、間に何が入っていても取れる。

```
/<node\b([^>]*?)(?:\/>|>([\s\S]*?)<\/node>)/g
```

（`packages/gis/src/osm-api.ts`。`parseOsmXml` は検証のために export してある。）

### `layer > 0` は「高架」を意味しない

OSM の `layer` は **交差する相手との相対的な重なり順**であって、
地面から浮いていることの根拠ではない。地上の線路が道路と交差するところにも、
建物の中を通る通路にも付く。浮いていることを示すのは `bridge` タグのほう。

`layer > 0` だけで高架にしていたときの実測（2026-09、東京駅周辺 4km 四方）:

| 誤って建てていたもの | 本数 | 例 |
|---|---:|---|
| トンネル・屋内の通路 | 92 | `tunnel=building_passage` の 30m の通路 |
| 駅構内の階段・通路 | 162 | 9m の階段、1m の footway |
| 線路の交差部だけ | 40 | 8m の `railway=rail` |

判定の決まり:

- `tunnel` が付いていたら建てない（`tunnel=building_passage` も含む）。
  `covered` では落とさない — 覆いのある高架が実在する（東北新幹線）
- `bridge` が無いものを建てるのは、**長く続いていて（250m 以上）
  かつ上の層にある**ときだけ。市街地の鉄道高架は OSM で bridge が
  付いていないことがあるので、そこだけ拾う
- 歩行者用（footway / steps / path / pedestrian / cycleway）は
  **`bridge` があるときだけ**。本物の歩道橋・ペデストリアンデッキには
  bridge が付く。無いまま上の層にあるものは駅の構内通路やビルの中の通路で、
  名前を見ると「JR秋葉原駅;3階;5番線」のようになっている

修正後、東京駅周辺で誤りは 0 になり、
鉄道高架は 309 → 190 本、歩道橋は 458 → 293 本になった。

### 信号のノードは車道の中心線上にある

OSM の `highway=traffic_signals` は **way の上のノード**に付く。
つまり車道の中心線上にある。そこに柱を立てると、**道の真ん中に柱が生える。**

実物は路肩（歩道の縁）に立っていて、そこからアームで車道の上へ
灯器を張り出している。道の幅の半分 + 路肩ぶんだけ寄せる。
日本は左側通行なので、進行方向に向かって左へ。

向きも道から取る。以前はすべて真北を向いていて、交差点のどの方向を
制御しているのか分からず、灯器を真横から見ることになっていた。

寸法の出典（交通信号灯器の設置基準・警察庁）:

| | 値 |
|---|---|
| 灯器（車両用 3 位・300mm 灯） | 0.94 × 0.35 × 0.28m |
| 灯器下端の高さ | 車道上 5.0m 以上 |
| 柱 | 根元 φ165.2mm / 上部 φ139.8mm |
| アーム | 車道上へ 2〜6m |

### 区画線は交差点の中まで引かれていない

実物の中央線・車線境界線・外側線は、交差点の手前の停止線で切れている。
切らずに引くと、交差する道の白線どうしが交差点の中央で重なり、
上から見ると白線が格子状に走って見える。

**交差点は道の端だけでなく途中にもある。** 端だけ切ると、
その道の区画線だけが交差点を突っ切る。累積距離で分断する。

交差点の見つけ方は「次数」。ある点に集まっている道路区間の端の数を数え、
3 以上なら交差点とする。way が途中で分割されているだけの点は 2 になる。
OSM は交差する道どうしにノードを共有させているので、
座標が一致するかどうかで数えられる（位置を作っているわけではない）。

**舗装は切らない。** アスファルトは交差点の中まで続いている。

浜松駅周辺 1km 四方の実測（2026-09）: 道路 574 本に対して交差点 288 か所
（うち信号あり 44）。区画線の形は 878 → 1,541 に増える（+75%）。
1 本の線が交差点で 2 本以上に分かれるため。

### `embankment=yes` は「盛土」であって高架ではない

OSM が `embankment=yes` と書いているのは **土を盛って持ち上げてある**
という意味で、柱の上に載っているという意味ではない。
これを無視してラーメン高架橋にすると、盛土の区間に径間 8.9m の柱が
延々と並ぶ。「高架じゃない所も高架になっている」と見えるのはこれ。

実測（2026-09、東京駅周辺 2km 四方）: bridge の無い構造物 35 本のうち、
東北新幹線・東海道新幹線・京浜東北線の盛土区間をそのまま高架橋にしていた。
盛土として組み直すと、この範囲の形の総数は 6,291 → 4,218 に減った。

`cutting=yes`（切土）も同じたぐいで、こちらは地面より下。構造物にしない。

盛土は柱ではなく壁で受ける。**法面（標準は 1:1.5）までは再現しない。**
高さ 9m の区間で片側 13.5m ぶん、実際には持っていない隣地まで
構造物が広がってしまう。OSM は擁壁か法面かを区別していないので、
狭いほう（擁壁）に倒す。

### 普通の道から高架へ上がる取付部

高架の端では路面が地表から数メートル上がったところで始まっている。
その手前の道は地表に描かれるので、間に段差ができていた。
実物ではそこに盛土や擁壁があり、道が緩やかに上がっていく。

使うのは実データだけ:

- **平面形** … 高架に端点を共有している OSM の way
- **上がる高さ** … その高架の路面高さ（すでに決まっている）
- **長さ** … 高さ ÷ 縦断勾配の上限

縦断勾配の上限（道路構造令 第 20 条 / 鉄道の省令解釈基準）:

| | 上限 |
|---|---:|
| 鉄道の本線 | 35‰ (3.5%) |
| 自動車専用道路（設計速度 60km/h 以上） | 5% |
| 市街地の一般道（40〜50km/h） | 7% |
| 歩行者・自転車 | 5% |

**端点を共有しているだけの脇道に取り付けてはいけない。**
高架に取り付く道は必ず高架と同じ向きに続いているので、
接続点での向きの差が 60 度を超えるものは外す。
これを入れないと、橋の脇の管理用通路が坂になる。

**道が足りないときは少しだけ急にする。** 高架に接する道が短く、
その先が OSM から取れていないことがある。標準の勾配にこだわると
上がりきる前に途切れて元の段差が残る。上限の 1.5 倍までは許す。
2 倍まで許したときは 14% の坂ができ、一般道には実在しない急さになった
（実測: 浜松・東京の 2km 四方で、上限を 1.5 倍にすると最大 9.7%）。

なお取付部の平面形は**地表にも道として描かれたまま**にする。
そこには実際に道があり、立体だけにすると接続先が見つからなかったときに
道が消えるため。二重に見えないよう、受ける壁は路面とほぼ同じ幅
（0.92 倍）で地面から路面まで塞ぐ。

### 高架に上がる階段は、上がった先からしか高さが決まらない

歩道橋・ペデストリアンデッキは必ずどこかで地表とつながっている。
その階段が無いと、デッキだけが空中に浮いて上がる手段が無くなる。

階段の高さは OSM に入っていない。入っているのは 2 つだけ:

- 階段の**平面形**（`highway=steps` の way）
- その端が**どの構造物につながっているか**（ノードを共有している）

つながった先の路面高さはすでに決まっているので、
「地表から、その路面まで上がる」ことは実データから決まる。
創作するのは段の寸法（蹴上げ・踏面）だけで、これは設計基準の値。

**接続先が見つからない階段は作らない。** 地下街への階段や法面の階段が
これにあたり、どこまで上がるのか分からない。推測すると実在しない構造物になる。

3 つはまりどころがある。

1. **端点の照合は「まとめる前」の座標で行う。**
   平行な歩道橋をまとめると中心線が最大 1.5m 動く。まとめたあとの
   中心線に対して 2.0m の許容で照合したところ、下をくぐっているだけの
   別のデッキ（1.34m）を拾い、階段 1 本を取りこぼした。
   OSM は同じ地点を指す way がノードを共有するので、
   まとめる前の座標なら距離 0 で一致する。許容は誤差ぶんでよい。

2. **路面高さは「まとめたあと」の値を使う。**
   まとめると id が変わり、接続部で段差が出ないよう高さも揃え直される。
   まとめる前の高さを使うと、上がりきったところに段差ができる。
   `sourceIds` で元の id から引き直す。

3. **踏面は基準値ではなく平面形の長さから割り出す。**
   蹴上げ 0.15m（立体横断施設技術基準）から段の数を決め、
   踏面 = 平面形の長さ ÷ 段の数 とする。踏面を先に決めて長さを
   逆算すると、実在しない位置まで階段が伸びる。
   割り付けた踏面が 0.21m（建築基準法施行令 第 23 条）を割るなら、
   その平面形は 1 直線の階段としては短すぎる（実物には踊り場や
   折り返しがあり、OSM がそこまで描いていない）。
   無い折り返しを作るのは創作なので、段は作らず斜めの構造だけを出す。

なお、階段は**地表にも描く**。`classify` は `highway=steps` に対して
必ず null を返し、地表の帯としての踏み跡は残す。
そうしないと、接続先が見つからなかった階段が地表にも立体にも
描かれない（線路と歩道で実際に起きた欠陥と同じ形）。

### 車線数の補完値から幅を逆算しない

OSM の道路タグの充足率は低い。浜松駅周辺 3km 四方の実測（2026-08）:

| タグ | 入っている割合 |
|---|---|
| `lanes` | 7% |
| `maxspeed` | 3% |
| `width` | 0% |

足りないぶんは道路構造令の標準値で補うが、
**補完した車線数からさらに幅を計算してはいけない。**
生活道路も 3 級道路もどちらも「対面 2 車線」に補完されるので、
逆算するとどちらも同じ 7m になり、道の格の違いが消える。

幅は「実データ → 実データの車線数 → 種別ごとの標準幅」の順で決める。
（`packages/gis/src/road-geometry.ts` の `roadWidthOf`。
 この誤りはテストが検出した。）

### 「地表に描かない」と「高架として建てる」は必ず同じ判定にする

高架は 2 か所で扱う。

- `structures.ts` … 高架として立体を建てる
- `road-geometry.ts` … 高架の区間は地表に描かない

この 2 つが食い違うと、**どちらからも描かれない道や線路**ができる。
エラーは出ず、ただ何も無い場所ができるだけなので気づきにくい。

実際に起きた。高架の判定を「layer > 0」から
「bridge があるか、250m 以上続いて上の層にある」に直したとき、
地表側は古いまま「layer > 0 なら描かない」だった。
結果、layer=1 の短い線路が高架としても建てられず、
地表にも描かれなくなっていた。

実測（2026-09、東京駅周辺 4km 四方）で消えていたもの:

| | 本数 |
|---|---:|
| `railway=rail`（東海道本線・京浜東北線など） | 68 |
| `highway=footway` | 41 |
| `highway=steps` | 23 |
| その他 | 4 |

浜松駅周辺では 0 本だった（線路がすべて bridge 付きの高架のため）。
地域によって出方が違うので、1 か所で確かめて安心してはいけない。

いまは地表側が `classify()` をそのまま呼ぶ形にしてある。
判定を分けて書くと、また離れる。

### `Number(null)` は 0 になる

クエリの数値を素朴に読むと、「指定が無い」ことと「0 が指定されている」ことを
区別できない。

```
const lat = Number(url.searchParams.get('lat'));   // 未指定なら 0
if (!Number.isFinite(lat)) return 400;             // 0 は有限なので通る
```

`/api/poi` はこれで、**引数の無い要求を「緯度 0・経度 0（大西洋）」として
受け付けていた。** 実際に 200 が返ることを確かめた。

`Math.min(Number('abc'), 20)` が NaN になるのも同じたぐい。
件数や半径が NaN のまま外部への問い合わせに渡っていた。

`packages/shared/src/geo.ts` の `parseNumberParam` /
`clampNumberParam` / `parseLatLngParam` を使う。
検証を 1 か所に集めておかないと、API が増えるたびに同じ穴が空く。

### 壊れた経路は「例外」ではなく「NaN」で来る

polyline のデコードは壊れた文字列でも例外を出さない。
`decodePolyline('!!!@@@###')` は緯度 -33.5 のような座標を 5 点返す。
経路エンジンの応答が壊れていても、そのまま案内が始まってしまう。

止め方を 3 段階に分ける:

1. **API で弾く** … `/api/route` が、座標が 2 点以上あり、
   すべて有限で地球上にあることを確かめる。壊れていれば 502 を返す
2. **ライブラリは落ちない** … 座標が空でも 1 点でも例外にせず、
   進捗 0 として返す。ここで落ちると画面が真っ白になる
3. **カメラの姿勢は必ず有限にする** … NaN を渡すとカメラが画面の外へ
   飛び、操作しても戻らない。`sanitizePose` で最後に落とす

測位（GPS）も同じで、まれに NaN を返す。そのまま進捗に入れると
距離も方位も NaN になり、正しい位置に戻っても復帰しなくなる。
`RouteFollower` は使えない位置を無視して前回の位置で進める。

### OSM のタグの値には上限を掛ける

OSM のタグは自由入力なので、入力ミスや荒らしで極端な値が入る。
`tracks=1000000000` をそのまま使うと、線路を 10 億本組み立てようとして
ブラウザが固まる（実際に固まることを確かめた）。

上限は実在するものの最大に合わせる:

| タグ | 上限 | 根拠 |
|---|---:|---|
| `tracks` | 40 | 世界最大級の駅でも 30 本程度（東京駅は 20 面 20 線） |
| `lanes` | 24 | 最多はカナダのハイウェイ 401 で往復 18 車線 |
| `width` | 100m | 道路の幅は最大でも 100m 程度 |
| `layer` | ±6 | OSM の慣習は -5〜5。立体交差でも 4 層で足りる |

**描く側でも同じ上限を掛ける。** 呼び出し側が忘れても固まらないように。

### 0 除算は「NaN が並ぶ」形で出る

`pickIndices(length, max)` は `(i * (length - 1)) / (max - 1)` で
添字を等間隔に取るが、`max` が 1 だと分母が 0 になり、
NaN の配列が返っていた。例外にはならず、そのまま座標に流れる。

**割る前に分母が 0 になりうるかを確かめる。**
NaN は例外を出さずに伝播し、描画側では「何も出ない」という形でしか
現れないので、原因にたどり着くのに時間がかかる。

地形の取得に失敗したときの NaN も同じ。標高を使う前に
`Number.isFinite` で確かめて、取れなければ 0（平地）として扱う。

### 速度制限は推測しない

`maxspeed` が入っていないときは表示しない。
種別から推測すると、実際とは違う数字を標識のように見せることになる。
`JP:urban` のような記号も数値ではないので採らない。

## 外部サービスの応答

### 配列があるはずの場所が `undefined` で来る

経路エンジン（Valhalla / OSRM）の応答は、混雑時や部分障害のときに
項目がまるごと欠けて返ってくる。`trip.legs` や `route.legs[].steps` が
無いまま HTTP 200 で届く。

そこに `for...of` や `forEach` を当てると `TypeError` になり、
**その英語の内部メッセージがそのまま利用者の画面に出る。**
実測で 7 通りの欠け方が例外になっていた:

| 欠けているもの | 出ていたメッセージ |
|---|---|
| `trip.legs` | `trip.legs is not iterable` |
| `trip.summary` | `Cannot read properties of undefined (reading 'length')` |
| `leg.maneuvers` | `Cannot read properties of undefined (reading 'forEach')` |
| 形状が空なのに案内がある | `Cannot read properties of undefined (reading '0')` |
| `routes[].legs` | `r.legs is not iterable` |
| `leg.steps` | `leg.steps is not iterable` |
| `maneuver.location` | `Cannot read properties of undefined (reading '0')` |

対処は 2 つ。

1. **応答の型を「省略可」で書く。** 仕様上は必須の項目でも `?` を付ける。
   必須で書くと、存在を確かめる分岐が「到達しない」と型検査に消される
2. **形にならなければ `RoutingError` で打ち切る。** 座標が 2 点未満なら
   経路として返さない。こうするとフォールバック側（OSRM）に回せる

数値の欠けも同じで、`m.length` が無いと `Math.round(undefined * 1000)` が
NaN になり、残距離も到着時刻も表示できなくなる。0 に落として先へ流す。

### polyline の文字列は連結してはいけない

polyline は「直前の点からの差分」で書かれている。
レグごとの `shape` をつないで 1 本の文字列にすると、
2 本目の先頭が「1 本目の末尾からの差分」ではなく
「原点からの差分」として解釈され、**経路が日本から飛ぶ。**

つないだ座標列から `encodePolyline` で符号化し直す。

### 案内の添字は 0 以上に収める

`begin_shape_index` が範囲外や負で来ることがある。
負のまま残すと `cumulative[index]` が `undefined` になり、
`?? 0` で 0 に落ちて「出発した瞬間に通過済み」の案内になる。
`[0, 座標数-1]` に収めてから記録する。

### LLM が書いた数値は範囲を確かめる

AI のツール呼び出しは、座標だけでなく**数値も信用境界**にある。
LLM は学習した別サービスの仕様をそのまま書いてくるので、
未対応の移動手段（`car`）、負の半径、上下が反転する俯角（-400 度）、
地面の中になる高度（0）が普通に届く。

座標を `knownPoints` で検証しているのと同じ理由で、数値も範囲に収める。
`Math.min(value, 上限)` だけでは負の値が素通りすることに注意。

### 環境変数の「空文字」は未設定ではない

`process.env.X ?? 既定値` は、`X=""` のとき **空文字を採用する。**
`??` が拾うのは `undefined` と `null` だけで、空文字は「値がある」扱いになる。

本番でこれを踏んだ。ホスティング側で環境変数を空のまま登録していたため、
エンドポイントが空文字になり、相対 URL のまま `fetch` して
`Failed to parse URL from /search?...` で **`/api/search` が 502** になっていた。
ローカルでは未設定（`undefined`）なので既定値が入り、再現しない。

対処は `packages/shared/src/env.ts` に集約してある。

```ts
envString(raw)    空白だけの値も undefined として扱う
envUrl(raw, fb)   絶対 URL でなければ既定値へ落とす（相対 URL も弾く）
envUrlList()      有効な絶対 URL が 1 つも無ければ既定値
envNumber()       数値にならなければ既定値
```

**環境変数を直接読まない。必ずこれらを通す。**
検証は `packages/shared/src/__tests__/env.test.ts`。

### API キーを URL のクエリに載せない

Gemini は `?key=...` でも受け付けるが、URL は
**アクセスログ・プロキシ・エラー報告にそのまま残る。**
`x-goog-api-key` ヘッダで渡す。

「フロントエンドに置かない」だけでは足りない。
サーバ側でも、鍵が写る先を増やさない。

### JSON の本文に入っている値は、型から確かめる

クエリ文字列は必ず文字列だが、本文には配列も `null` も NaN も入る。
`{ lat: '34.7' }` や `{ lat: NaN }` をそのまま使うと、
NaN を含む URL を組み立てて外部サービスに投げてしまう。
`packages/shared/src/geo.ts` の `readLatLng` を通す。

**システムプロンプトに入る文字列からは改行を落とす。**
都市名をそのまま埋めると、`# 絶対に守るルール` のような見出しを
偽装して差し込める。

## PLATEAU

### 神戸市には 3D 都市モデルが無い

datacatalog に建物モデルが存在しない。対応都市から外し、
LOD2（テクスチャあり）が揃っている **姫路市（28201）** に差し替えた。
対応都市を増やすときは、まず datacatalog に実データがあるか確かめる。

### near と far が同じ四分木を指すことがある

浜松では近景用と遠景用のタイルセットが同一の四分木を返していた。
結果、同じ建物が二重に描かれ、タイルの取得も 2 倍になっていた。

`packages/map-engine/src/buildings.ts` の `needsFarTileset(city)` で、
近景がすでに直接タイルセットを指している都市では遠景を作らない。

### Cesium は tileset.json のクエリを子へ引き継ぐ

`Cesium3DTileset.fromUrl('/api/tileset?city=tokyo&bbox=...')` と読ませると、
その tileset の中の子 tileset.json やタイル本体（b3dm）にも
**同じクエリがそのまま付いて**飛ぶ。実機ブラウザでの実測（2026-09）:

```
https://assets.cms.plateau.reearth.io/.../13101_chiyoda-ku_.../tileset.json
  ?city=tokyo&layer=near&bbox=139.7395,35.6588,139.7948,35.7037&model=textured
```

`Resource` が `queryParameters` を派生先へ継承する仕様による。

bbox はカメラが動くたびに変わる。つまり **同じタイルが毎回ちがう URL になり、
ブラウザにも CDN にも一切キャッシュが効かない。**
街を往復するだけで同じ建物を何度も取り直していた。

条件はパスに書く。

```
/api/tileset/{都市}/{レイヤ}/{建物モデル}/{bbox}/tileset.json
```

クエリが無ければ引き継がれるものも無い。
bbox は小数 4 桁（およそ 11m）に丸める。細かくすると、
カメラが少し動いただけで別の URL になってキャッシュが当たらない。

### 地形を待ってから建物を読むと、地形が遅いぶんだけ街が出ない

起動時に `await setTerrain()` してから `loadCity()` を呼んでいた。
実機ブラウザで地形サーバへ到達できない状態にして測ると（2026-09）:

| | 建物の tileset.json を要求した時刻 |
|---|---:|
| 地形を待つ（前） | 13,360ms |
| 地形と並べる（後） | 672ms |

失敗と判定されるまでの 13 秒、建物を 1 本も取りに行っていなかった。

建物の 3D Tiles は絶対座標を持っていて、地形とは独立に置ける。
待つ理由が無い。どちらか片方が落ちても、もう片方は表示できる。

測り方: `npx tsx scripts/measure/startup-requests.mts`
（Chromium は環境に入っているものを使う。`playwright install` は実行しない）

### テクスチャ無し版は整備範囲が狭い

同じ地域について、PLATEAU は 3 通りの配信を持っている。

```
13-bldg-maxlod2-latest             62 市区町村   LOD2 ＋ 実写テクスチャ
13-bldg-maxlod2-notexture-latest   45 市区町村   LOD2（テクスチャだけ無い）
13-bldg-maxlod1-latest             62 市区町村   LOD1（高さだけの箱）
```

**テクスチャ無し版だけ 45 市区町村しか無い。**
「テクスチャ無し」を選んだだけで未整備の区から街が消えないよう、
BFF は範囲に中身が無ければ元の指定へ戻す。

このとき **LOD を落としてはいけない。**
`lodFallbackChain` に任せると maxlod2-notexture → maxlod1 と落ち、
「用途で塗り分け」を選んだだけで箱型になる（＝選んでいないものが出る）。
`maxlodN` は「利用可能な最大 LOD（N 以下）」なので、
LOD2 が未整備の地域でも配信側が LOD1 を入れてくれる。
建物のベースでは LOD を落とす必要がそもそも無い。

そして **戻したことを呼び出し側に伝える。**
要求した値のまま用途色を塗ると、実写テクスチャの上に色が乗って
「事実どおりの色」でなくなる。tileset.json の `extras` に
実際に配信した種別を入れ、Cesium 側は `tileset.extras` で読む
（レスポンスヘッダは Cesium からは読めない）。

### LOD1 は「軽い」とは限らない

千代田区の実測（b3dm を等間隔に 19 枚取った平均、2026-09）:

| | タイル数 | 1 枚の平均 | 区全体 |
|---|---:|---:|---:|
| LOD2 テクスチャあり | 633 | 695KB | 約 440MB |
| LOD2 テクスチャなし | 633 | 345KB | 約 218MB |
| LOD1 箱型 | 20 | 4.65MB | 約 93MB |

LOD1 は総量こそ最小だが、四分木が浅く 1 枚が 4.65MB もある。
視界に 3 枚入れば 14MB を読むことになり、通信では有利にならない。
軽くなるのは頂点数と描画のほうで、そこは桁違いに減る。

テクスチャを外すほうは、タイルの分かれ方が同じまま総量がほぼ半分になる。
範囲で絞る効き方も変わらないので、素直に軽い。

なお LOD1 のバッチテーブルにも `bldg:usage` と `bldg:measuredHeight` が
入っている（千代田区 data19.b3dm で確認）。箱型でも用途で塗り分けられる。

### 端をかすめるだけの区まで開いてしまう

東京は 8 区にまたがるが、そのうち 4 区は表示範囲の端をかすめるだけで、
それが総タイル数の半分を占めていた。

`app/api/tileset/route.ts` で、重なり **面積**の大きい順に並べ、
上限（近景 5・遠景 10）まで残す。
これで tileset.json が 4.3MB → 2.2MB、タイル数が 3,555 → 2,571 になった。

## 座標と幾何

### 方位角の計算に `cos(緯度)` を忘れない

経度 1 度あたりの距離は緯度によって変わる。
これを忘れると柱が構造物に対して斜めを向く。
北緯 34.7 度では約 18% ずれ、45 度方向の柱の見付けが √2 倍に膨らむ。

検証: `elevated-structures.test.ts` の
「斜めに走る高架でも柱が構造と平行に立つ」が実際に見付け幅を測っている。

### 高さの基準は「路面」から下へ取る

桁下を基準にすると、同じ路線でも構造形式が変わる接続部で路面に段差ができる
（実際に 1.2m の段ができていた）。

```
deckTop    = 地盤 + deckHeight   路面（軌道面・車道面）
slabBottom = deckTop - 版厚      床版の下面 = 梁の上面
beamBottom = slabBottom - 梁高   梁下。柱の頭でもある
```

さらに、つながっている構造物どうしで路面高を揃える（`alignDeckHeights`）。
